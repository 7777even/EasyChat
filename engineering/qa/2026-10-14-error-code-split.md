# QA — 拆分被复用的通用错误码

- 日期: 2026-10-14
- 效率等级: **L4**（`openspec/changes/2026-10-14-error-code-split`）
- 范围: `ResponseCodeEnum` 新增两码；**3 处调用点**改码（限流 1 + 验证码 2）；前端 `Request.js` 拒绝对象结构化
  + `Login.vue` 按码分流；新增门禁 `verify_error_code.mjs`。**数据库零变更**。

## 验收口径

- **C1**：限流有独立码 `1004`，客户端据此倒计时，监控可单独告警。
- **C2**：验证码失败有独立码 `1005`，客户端清空并聚焦输入框（**不自动重发**，重发接口本身受同一限流约束）。
- **C3**：错误码分段与前后端同步由门禁锁住；**新码不得「定义了从未使用」**。
- **兼容性**：老客户端遇到 1004/1005 必须落到默认分支、照常 Toast `message`，行为与变更前一致。
- **DoD**：929 后端 + 786 前端全绿；新增断言**均经探针证明有判别力**；生产行为零回归。

### 判别力实证（**先造反例，再谈覆盖**）

门禁探针 **9/9 全部捕获**，含：前端摘掉任一新码、拒绝对象不带 `code`、不带 `rateLimitSeconds`、
**把 1001 写成特殊处理**（破坏向后兼容）、默认分支不再用 `message`、
前后端窗口秒数脱节（两个方向各测）、**前端引入幽灵码**。
还原确认字节一致。

## 过程中查出的 4 个问题（**都是我自己的错误，不是环境问题**）

1. **「前后端双向对账」是写错的规格。** 实测前端 `ErrorCode` 只 **11 个**码、后端 **40+** 个 ——
   前端**本来只声明「用得上的子集」**（2202、2301~2307、2401…2705 均未声明）。
   按我 spec-delta 里写的「两侧都不得存在对方没有的项」，该门禁会**永久报红**。
   → **已订正为单向**（仅禁止前端引用后端不存在的「幽灵码」），并把这段经过写进 spec 与门禁注释。
   **教训：规格写错时要改规格，不能责令现实迁就**。
2. **向后兼容断言形同虚设。** 初版只查 `code == ErrorCode.PARAM_ERROR` **一种写法**，
   探针换成 `responseData.code === ErrorCode.PARAM_ERROR` 就溜过 → **一换写法就失效的断言等于没有断言**。
   已改为「剥注释后 `PARAM_ERROR` 不得出现」。
3. **判定边界写错导致恒假。** 初版假设「拒绝对象带 code」是内联对象字面量，
   实际实现已抽成 `buildReject` 辅助函数。已改为**只取该函数体**判定（§2.1 第 8 条）。
4. **一条关于测试引擎的错误结论必须订立正。** 我在 TURN Change 写下「本仓是 JUnit 4，
   JUnit 5 会静默不执行」，并据此写进任务注释。**实测为错**：
   后端 **23 个** JUnit 5 测试类全部正常执行，JUnit 4 类 42 个也在跑。
   **真因**是：用 `-Dtest=类名` **过滤**运行时会漏掉 `@Nested` 内部类的测试
   （实测：过滤时 1/2，全量时 2/2）。我当时正是用过滤验证含 `@Nested` 的红阶段，
   才把「过滤导致 0 执行」误诊成「引擎不执行」。

## 证据

- 探针脚本可复跑，输出含 `[捕获]/[漏网]/[无效]` 三态 + 汇总行，且**还原确认**。

## 结论

**达成**。C1–C3 落地；兼容性由断言锁住；门禁已接 CI 并登记 §10/§3.1。

**本 Change 最实质的收益不是「码好看」**：拆码前 `RateLimitBehaviourTest` 因限流与
验证码共用 1001，被迫三次改用**文案**判定，且因 `getContentAsString()` 默认
ISO-8859-1 解码而**恒真**（靠变异检验才发现）。拆码后该断言回到最稳固的 code 判定形态。

**已知边界（有意不做，已获人工确认）**：`CODE_1001` **仍承载 6 类语义**
（HTTP 绑定失败 / Bean Validation / 业务规则校验 / 权限性校验等）。
它们处理方式一致（「改输入」），全量归类会大幅放大回归面而用户可感收益为零。
