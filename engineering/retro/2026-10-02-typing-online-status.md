# Retro — 输入状态与在线状态实时感知（收尾）

- 关联 Change: openspec/changes/2026-09-30-typing-online-status
- 关联 QA: engineering/qa/2026-10-02-typing-online-status.md

## 做得好

1. **仓库门禁提前建好，才能在收尾阶段一键定位断点**。`check-ipc-registration.mjs` 是 2026-09-26 的 QA 附带发现（system-facts §13 有记），这次直接给出「哪两个通道没注册」的确切答案。若没有它，这次收尾只能靠人肉 grep 三层文件。
2. **「静默失效」被当成一等公民治理**。主进程 IPC 采用「定义 + 导出 + index.js 调一次」的显式模式，代价是啰嗦，收益是配合门禁后**漏注册会在提交前被拦下**，而不是等到用户投诉。

## 问题

1. **功能从未真正工作过，却一路走到归档**。`tasks.md` 里阶段三/四（主进程、前端）全标 `[x]`，但主进程通道没注册——「代码写了」被当成了「功能可用」。
2. **2026-10-01 的复核只查了「文件存不存在」，没查「链路通不通」**。复核结论写着 `git grep -c` 命中 2、前端三处命中，就据此判定已落地；而真正决定成败的 `index.js` 调用不在任何 grep 范围内。
3. **该变更的 spec 从未回写**，`openspec/specs/` 下无 `typing-online-status`，导致「系统现在是什么样」这条基线缺失。

## 原因

- 验证口径偏向**存在性**（文件在、函数在、引用在）而非**可达性**（事件真能到达对端）。
- 归档检查（hygiene）只校验 tasks 是否全勾，不校验勾选内容是否属实——**勾选框是人写的，机器只能验证形式**。

## 改进方案

| 优先级 | 方案 | 落点 |
|--------|------|------|
| 高 | hygiene 门禁增加一条：Change 若涉及前端主进程/preload，必须能对上 `check-ipc-registration` 的通过结果，否则提示未验证 | `scripts/check-openspec-hygiene.mjs` |
| 高 | QA 模板增加「可达性验证」必填项：列出该功能的关键一跳及其验证方式（门禁/活体/日志），而非只列编译与构建 | `templates/_qa_template.md` |
| 中 | 为「渲染层 → preload → 主进程 → WS」这类跨层链路，考虑补一个最小的 Node 侧进程内测试（不发网），验证事件能被 handler 收到 | 后续评估 |
| 中 | 归档前自查清单增加「该功能用户可感知吗？用户怎么触发？触发路径每一跳都有验证吗？」 | `templates/_openspec-tasks_template.md` |
