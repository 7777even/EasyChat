## 问题

- **同一个 `JSON.parse(null)` 陷阱踩了两次**：先是「单聊不写 atUserIds」用例，
  后是「普通成员手打 @所有人」用例 —— `buildExtraData` 在无附加信息时返回 `null`
  而非 `'{}'`，`JSON.parse(null)` 得 `null`，取属性即 TypeError。
  第二次已在文件顶部加了 `extraOf()` 助手并写明成因，但**第一处直到踩了才知道**。
- **我自己写的门禁踩了我自己写的纪律**：`verify_at_mention_core.mjs` 的 B6 断言
  「核心不得含 axios」，而核心的 JSDoc 里正好写着「本模块不 import electron / window /
  **axios** / store」——**把自己的注释判成了违规**，正是 AGENTS §2.1 第 7 条描述的场景。
- **写门禁时才发现自己的注释会造成「双份正则」误报**：为说明「本轮刻意不动正则」
  而在注释里写了正则形态，若门禁直接数出现次数会算出 2。剥注释后才是正确的 1。
- **UI 截图证据缺失**：前端 AGENTS §4 要求 UI 改动必附截图，我直到写 QA 时才意识到
  沙箱根本给不出。**DoD 里有这一项，但我没有在动手阶段就把它标成不可达。**

## 原因

- **`null` 与 `'{}'` 的语义差别在人读代码时不可见**：`buildExtraData` 返回 `null`
  表达的是「服务端拿不到 extraData」，这是个**有意的设计**，但只在函数末尾
  `Object.keys(extra).length > 0 ? ... : null` 一行里体现。断言者若不复现这条路径就必踩。
  → 对「返回可空结构」的函数，测试助手应**在第一次用到时就出现**，而不是第二次。
- **纪律文档解决不了「自己的注释」**：AGENTS §2.1 第 7 条我读过，也记得，
  但写门禁时是新上下文，没有把「本仓注释爱引用反模式」这条自动应用到**自己新写的文件**上。
  → 已在门禁顶部写明该纪律并附上本次的具体踩坑，使后来者能对上号。
- **DoD 的可达性没有在计划阶段校验**：我在 `tasks.md` 里把「UI 证据（页面截图）」列为
  DoD 项，却没有在 T0 阶段确认沙箱能否产出。**DoD 项若早注定不可达，应该在计划里就降级
  或改成可替代的证据形式**（如本例可改为「录屏/手工验证脚本 + 用户现场确认」）。

## 改进方案

- **新增「可空返回」测试助手约定**：凡返回 `string | null` / `T | null` 的函数，
  其测试文件**首个** helper 就是安全解析助手（`extraOf` / `parseOrNull`），
  不允许裸 `JSON.parse(fn(...))`。可考虑做成共享 test util。
- **门禁文件顶部强制写「本仓注释爱引用反模式」**：所有「不得包含」类断言默认走
  `stripComments`，且**门禁自身要先对自己的注释做一次自检**（本次 B8 就是这个作用）。
- **计划阶段校验 DoD 可达性**：写 `tasks.md` 时对每条 DoD 标注「沙箱内可产出 / 需外部条件」，
  不可达项当场替换为替代证据或直接删除，不要留到最后写 QA 时才发现。
- **抽离类 Change 的变异清单固定包含三条结构用例**：① 组件内联判定 ② 组件复制第二份
  正则/常量 ③ 关键状态未传入核心。本项目已因 `callStoreCore` 与本次两次踩过「抽离后被绕过」。
- **UI 改动的 QA 证据分级**：无 GUI 时把「端到端行为」改由**组件级 mount 测试**覆盖
  （本例本可用 `mount` 断言 `buildExtraData` 的传参），而非留空。
