# Retro — Flyway 迁移自动化（2026-10-04）

- 关联 QA：`engineering/qa/2026-10-04-flyway-migration-automation.md`
- 等级：L4

## 一、做得好

1. **tasks.md 把「阶段零：先实测再动手」排在所有实现之前**。
   正是这个排序让三次假设推翻全部发生在写实现之前、且都被留档。
   如果先写完门禁和 compose 再验证，整个变更会建立在一个错误前提上。
2. **证据用真机而非推断**。`Error 1060`、`FlywayEditionUpgradeRequiredException`、
   `Successfully validated 12 migrations`、`history: 004 im-complete success=1`
   都是跑出来的。「实测 5」用的是「先 DROP 掉 8 列 → 看它们是否回来」，
   比读日志更有说服力。
3. **失败证据同样留档**。004 首次执行的 `Error 1064`、8.0.4 的版本报错都写进了 `engineering/qa/`，
   而不是删掉重跑。
4. **手抄 SQL 改为程序化生成**。改 004 时用 `git show HEAD:` 取原文 + 脚本替换，
   保证未触及部分逐字节不变。这直接避免了一次未授权改动。
5. **变异检验两次抓出假门禁**（详见 QA §6）。若无变异，本批会交付两个
   「存在但无判别力」的断言 —— 而它们看起来是绿的。

## 二、问题

1. **我在 design 里押错了三个假设**，且都是「看起来显然」的那种：
   版本随 parent 就行、快照能在增量之上跑、`DELIMITER` 大概能过。
2. **变异脚本第一版把「锚点没命中」报成 `[ERROR]` 但整体判失败**，
   看起来像「变异没生效所以不算漏网」，实际是**我的 harness 有 bug**。
   若当时没逐条读输出，会误以为 13 个用例都验证过了。
3. **门禁里用了 PCRE 的 `\Z`**。JS 正则里它是字面量，前瞻永不成立 ——
   断言拿到的「块」是整个文件后半段，却仍返回 PASS。
4. **preflight 脚本只读 properties 不读 env**，堵死了它自己在报错里建议的处置路径。
   这是自曝 bug，靠「照着自己写的报错信息走一遍」才发现。

## 三、原因

1. **假设替代了验证**。写 design 时我把「Flyway 是标准工具、parent 会管版本」当成了事实，
   没意识到「parent 管的版本恰好不支持本项目实际在用的 MySQL 版本」这种组合完全可能。
   根因是**没先确认本项目的真实环境**（本机 5.7 vs compose 8.0 这个矛盾在文档里就写着，
   我却是在撞墙时才注意到）。
2. **harness 的失败模式没有设计**。「锚点未命中」在语义上是「这个用例无效」，
   但我让它和「变异生效但门禁没抓到」共用一个出口。
3. **正则里的前瞻不验证边界**。用 `(?=...)` 切块时没想过「这个断言在这门语言里是否成立」。
4. **没有从使用者的角度走一遍**。闸门的报错信息是我写的，我给运维的建议也是我写的，
   但我从未验证「运维照着做能不能走通」。

## 五、对遗留的明确判断

- **遗留 #10（6/12 迁移非幂等）**：用户决策不修，我同意。Flyway 版本表已保证
  「每个迁移只执行一次」，补守卫的边际收益低于其引入的 SQL 可读性成本。
  但**必须在三处文档写明「不要手工重跑这六份」**（已写）——否则下次有人
  「帮个忙重跑一下」就会撞 1060，且那时他不会知道这是设计决策。
- **遗留 #11（拒绝分支方向不可静态检测）**：这是**诚实的登记**，不是遗留缺陷。
  要机控得改写成可注入依赖的模块并上测试框架，属 L3。当前用真机验证兜底更划算。
