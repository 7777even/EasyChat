# Retro — 管理端消息删除位（delete_flag + 20 帧实时同步）

- 日期: 2026-09-29
- 效率等级: L4

## 做得好

- L4 关卡先行：三项决策（delete_flag 语义 / 新增 20 帧 / 过滤+残余增强）一次性人工拍板留痕，实施期零返工。
- 四件套追溯矩阵闭环：proposal Capabilities ↔ spec-delta Requirement ↔ tasks 编号逐条对齐，归档回写时直接机读合并。
- 冒烟脚本一次写全 P0–P4 并带 `finally` 回滚，fixture 全自动还原，脚本可重复执行（run-unique 关键词防串扰）。
- 推送断言采用「队列轮询 + 双编码解码」，规避毫秒级竞态与 Redis 序列化器差异，首跑即 43/43。
- 事务后推帧（`afterCommit`）+ 幂等守卫设计在冒烟 P2 得到实证：重复处置不改写、不重推。

## 问题

- 首跑冒烟两处失败：① Redis 离线队列值经 `RedisSerializer.json()` 双编码，`json.loads` 一次得到 str；② 异常时 `state` 在函数内部创建未传出，`finally` 清理拿到空 state 跳过回滚，DB 残留 `delete_flag` 与举报/审计行。
- `wsClient.js` case 20 插入时在无 `{}` 块的 case 组后多补一个 `}`，`npm run build` 解析失败一次。
- 首跑前手工清理残留 + 二次冒烟额外耗时约 20 分钟。

## 原因

- 对目标中间件的序列化配置（`RedisConfig` value=JSON 序列化）与脚本读取侧未先做最小实证，直接按裸 JSON 假设编写。
- 「清理所需的运行时状态」与「执行逻辑」耦合在同一栈帧，异常路径下状态丢失——回滚逻辑应持有共享状态句柄，而非依赖正常返回值。
- 编辑长 switch/case 结构时凭上下文记忆判断括号归属，未先读全 case 块边界（case 2 组实际无 `{}`）。

## 改进方案

- 读写外部存储（Redis/MQ/序列化对象）前先跑 10 行级诊断脚本实证「键形态 + 值编码」，再写正式断言。
- 凡带 `finally` 回滚的冒烟脚本，`state` 一律在入口创建、以参数传入执行函数，异常路径也能拿到半程状态完成回滚。
- 编辑既有控制结构（switch/大段模板）前先完整读取目标块边界；改完必跑构建再进入下一项，避免错误累积。
