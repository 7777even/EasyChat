## 一、做得好

1. **顺藤摸出既有缺陷并当场修**。冒烟首跑 33/39，6 条失败全指向「拉黑根本没加上」。顺着查下去发现 `removeUserContact` 拉黑走 `updateByUserIdAndContactId`，**对不存在的行是 no-op** —— 搜索到的陌生人从未成为好友，没有行可更新，于是「界面上加了黑、实际啥也没发生」。这是 `UserDetail.vue` 那个按钮上线以来一直存在的坑，靠纯读代码和单测都发现不了，只有真跑一次活体才暴露。
2. **既有测试把缺陷固化了，这比没测试更危险**。`removeUserContact_blacklist` 原本断言 `update` × 2 —— 它**正确地描述了错误的行为**。如果我只加新功能不碰这个测试，缺陷会带着"绿色测试"的伪装一直活下去。改成断言 upsert 语义 + 补 `removeUserContact_delStillUsesUpdate` 护栏。
3. **变异检验替代 TDD 红阶段**。我没走完整 TDD 顺序（补方法签名时顺手把实现写了），于是对安全守卫做了一次变异：把 `!BLACKLIST.equals(status)` 去掉，安全红线用例立刻转红。**测试的价值不在于绿，在于它变红时确实是因为它该变红。**
4. **design §6 的风险预警真的救了我**。风险表里写「`icon-lock` 若不存在则改用已验证存在的图标名」—— 结果 `iconfont` 里**根本没有 lock**。写风险时顺手去核一下字形表，就能省掉一个空白方块的 UI 缺陷。
5. **安全红线的守卫设计是双向思考的**。「我能不能解除别人拉黑我」和「我解除时该不该删对方的行」是两个不同的问题。第二个问题容易漏：双方互相拉黑时，删掉对方那行等于替对方解除拉黑。加了 `status=BLACKLIST_BE(5)` 守卫，冒烟 §5b 专门验证这条。
6. **契约门禁真的有判别力**。接前端前它报「3 个潜在孤儿」，接完归零。回想批次 1 那个 `eslint .` 的教训 —— 门禁要么有判别力要么没有，**不存在"有总比没有好"**。

## 二、问题

1. **TDD 顺序没走对**（本批最实质的问题）。首轮编译失败（方法不存在），我补方法签名时直接把实现写了，跳过了行为级红。虽然后面用变异检验补了证据，但**顺序错了就是错了**：红阶段会逼出"这个断言到底想验证什么"，而我跳过后是靠变异反推的。
2. **我又一次在 edit 时误删了代码**。给 `UserInfoController` 插新端点时，`oldString` 匹配到了「退出登录」那段，替换后把 `@GlobalInterceptor` 和方法签名一起删掉了。是紧接着读文件才发现的。**每次编辑大文件后必须回读确认**，不能凭"edit 成功了"就往下走。
3. **`removeUserContact` 是个三方共用的方法**（拉黑 / 删好友 / 群成员管理各有分支），我在里面插分支时其实应该先问一句"这个方法的语义边界是什么"。现在的实现是「BLACKLIST 走 upsert、DEL 走 update」这种按枚举分支的混合语义，能跑但不够显式。
4. **冒烟脚本建了 6 个关系行组合但没有独立的"前置校验"**。§5 手工 INSERT 造双向拉黑，如果中途某步失败，finally 只按 `u != v` 删，理论上不会误删真实好友 —— 但 A 和 B 原本**可能**是好友（本次清理把他们的关系也删了）。这次恰好 A、B 互不为好友所以无损，但脚本对存量数据是有风险的。
5. **前端 53 条新 CRLF 告警**。第三次撞上 prettier `endOfLine` 与 git `autocrlf` 未对齐的问题。
6. **iconfont.json 不是合法 JSON**（编码损坏），`ConvertFrom-Json` 解析失败，只能靠读原始文本提取字形名。资产文件本身有问题。

## 三、原因

1. Java 里给"全新方法"写 TDD 有个真实的摩擦：测试引用不存在的方法 → 编译失败 → 你必须先加签名。多数人（包括我）在这一步就把实现补完了，因为"只加个抛异常的桩"感觉是多余的一步。**但那恰恰是红阶段的全部价值所在。**
2. 没有养成"编辑后回读"的肌肉记忆。`edit` 工具返回成功只代表字符串替换成功，不代表语义正确。
3. 既有方法被多个调用方复用时，缺少对"该方法应承担哪些语义"的显式声明。`removeUserContact` 的三个调用方各自需要不同语义，硬塞进一个方法靠枚举分支区分，是历史遗留。
4. 冒烟脚本缺少"只清理自己造的数据"这一约束的显式表达。我用了"删掉 A/B/C 之间全部关系"的粗暴做法，赌的是他们本来没关系。
5. prettier 配置与 git core.autocrlf 全局未对齐，第三次了。
6. 图标字体资产疑似在某次批量编码转换中被破坏。

## 五、给下一批的经验

- **冒烟能抓到单测和读代码都抓不到的东西**。「拉黑陌生人静默失效」就是一个活例子：它语法正确、类型正确、有测试覆盖（覆盖的是错误行为）、静态检查全绿——只有真跑一次才现形。**冒烟不是可选项。**
- **绿色的测试可能是错的**。看到既有测试与新发现的现象冲突时，先怀疑测试，别急着怀疑实现——我这次是实现对、测试错，但反过来的情况同样会发生。
- **安全守卫要双向想**。不只是"我能做什么"，还有"我做了之后对别人意味着什么"。双向删行这个设计就是从"对方会看到什么状态"倒推出来的。
- **新方法的 TDD 桩不要省**。多写三行 `throw new UnsupportedOperationException()`，换来的是"我到底想验证什么"被逼出来。
- **edit 之后回读**。工具返回成功 ≠ 代码正确。
