# Retro — 敏感词库管理端（CRUD + 批量导入导出 + 热更新）

- 日期: 2026-09-26
- 效率等级: L4

## 做得好

- **两道 L4 关卡都前置拍板**：提案阶段就把 `delete_flag` BIGINT 时间戳语义与 2704/2705 错误码两项高风险决策摆到人工确认，用户一句「两关都过，开工」后实施全程零返工、零契约变更。
- **把上一个 Change 踩过的坑写进本 Change 的验收断言**：report-admin 的 `bean.` 前缀问题在本次 Mapper XML 写作时即按约定落笔，冒烟一次通过，未复现同类 `BindingException`。
- **唯一索引方案在设计期就闭环**：`(word, delete_flag)` 让「逻辑删除」与「删后重导」共存，冒烟第 2、4 组直接把「删后重增」「删后重导」写成断言，实测通过。
- **冒烟脚本首跑就抓出真缺陷**：往返导出（导出加 `'` 防公式注入、导入未剥离）在第 4 组断言暴露，当场修复后复跑全绿——这正是 C3「往返等价」写进验收标准的价值。
- **性能细节主动优化**：导入查重从「逐行点查」改为「一次性载入 HashSet」，5000 行上限下避免 5000 次往返。

## 问题

- 冒烟首跑 8/49 误报 FAIL，全部源于断言基座 `code_of()` 没处理 `post()` 返回的 `(status, json)` 元组（复用 report-admin 脚本片段时的疏漏），浪费一轮跑查。
- `design.md` §4 写的 `word ≤64` 与 DB 实际 `varchar(50)` 不一致，是在校验逻辑落地时才发现的，靠 QA「未运行项」如实标注收口。
- 前端菜单图标先写了个 iconfont 中并不存在的 `icon-filter`，靠「逐一核对图标名」才发现，`icon-warning`（举报管理在用）同样不存在，属既有隐患。
- Electron 桌面 UI 仍无自动化截图链路，QA 必附截图的要求只能以「构建 + 代码审查」替代并如实记入未运行项。

## 原因

- 复用旧脚本的公共函数时只看了调用处、没重读函数签名，缺少「复用即复核」动作。
- 规格文档字段长度凭印象写，未先 `SHOW CREATE TABLE` 对齐真源；设计与 DB 基线之间没有机械校验。
- 图标这类「查了才知道」的资源没有可校验清单，靠肉眼比对 CSS；且未意识到既有页面也踩了同坑。
- 前端截图依赖 Electron 运行态，仓库内没有 headless 启动 + 截图的既有工具链。

## 改进方案

- 冒烟脚本凡复用既有函数，先重读其返回类型并在首条断言前加一条「基座自检」（断言 `code_of` 对典型成功/失败样本返回预期值），基座错则整轮不白跑。
- 涉及 DB 字段的 design §数据模型，落笔前必先跑一次 `SHOW CREATE TABLE` 快照贴进 design 或 evidence；QA 时将「design 字段长度 vs 基线」列入核对项。
- 用到 iconfont / 枚举类资源时，先用 grep 在资源文件里确认存在再引用；发现既有同类缺失（`icon-warning`）单独开 L1 修复。
- 排期补一条 Electron 冒烟路径：dev 启动 → 走到目标页面 → 截图存 `engineering/qa/`，补齐前端 AGENTS.md §4 的截图证据要求。
