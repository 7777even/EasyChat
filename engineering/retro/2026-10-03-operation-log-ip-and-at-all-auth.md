# Retro — 审计日志补记客户端 IP + @所有人 权限下沉服务端

- Change: `openspec/changes/2026-10-03-operation-log-ip-and-at-all-auth/`
- 日期: 2026-10-03
- 分级: L4

## 一、做得好

1. **先核实「单点校验是否真的全覆盖」再动手**。动手前查了 `saveMessage` 的调用方，
   确认**全仓仅 1 个外部调用方**（`ChatController:179`），内部只有一处机器人自回复。
   若跳过这一步，很容易做出一个「以为拦住了、其实 WS 侧还有个后门」的补丁——
   而这类补丁比不修更危险，因为它让人以为问题解决了。
2. **ADR-001 让 6 处调用点零改动**。调用点都在 Service 层、不持有 `HttpServletRequest`，
   「让它们传真实 IP」在架构上根本走不通。改为在 `recordLog` 内部补齐后，
   额外收益是：**将来新增调用点默认就带 IP**，不存在「新加一处又忘了传」的漏网。
   审计类字段最怕的就是这种逐点维护。
3. **把限流的 IP 解析合并成单一实现**。此前 `GlobalOperationAspect` 有私有
   `resolveClientIp`，若只给审计新增一份，就会出现「限流按一套规则、审计按另一套规则」，
   事后对不上账却没人知道。抽出 `IpTools` 后这个隐患从结构上消失。
4. **`isAtAll` 的默认倾向选 false，且理由写进了注释与单测**。两个误判方向后果**不对称**：
   误判 true → 普通成员发不出消息（功能故障，用户只会说「发不了消息」，极难定位）；
   误判 false → 权限绕过（本批要堵的洞）。所以只认**顶层布尔**——
   这条约束直接体现在 `instanceof Boolean` 而非 `getBoolean()` 上，
   因为 fastjson 会把 `"1"` / `1` 宽松转成 true，正是误判 true 的来源。
5. **职责切分清晰：单测管行为，门禁管结构性位置**。「atAll 校验必须在 `ROBOT_UID` 判断之内」
   是跨分支的控制流位置，单测表达不了；门禁用 `indexOf` 比较位置来断言。
   变异检验验证了这条断言真的会红。

## 二、问题

1. **冒烟脚本一度显示「B 的所有消息都 1002」，几乎被误判为新代码把发送链路打挂了**。
   真实原因是 fixture 用 `LPUSH` 写裸串 `G90062243340`，而 `RedisUtils#getQueueList`
   用 **Jackson 逐元素反序列化**，裸串抛 `SerializationException`。
   **是这个症状最凶险的地方**：它同时打挂了「审计冒烟」和「@所有人 冒烟」，
   看起来像新引入的 P0 故障。**靠后端日志才定位到真因**——若没有日志就只能靠猜，
   而「猜错方向」意味着会去改本来正确的生产代码。
2. **我给冒烟脚本写的第一条错误注释是错的**：`/group/saveGroup` 我先写成
   「返回 `Result<Void>` 拿不到 groupId → 改调 `loadMyGroup` 反查」，但真实卡点是
   **新建群强制要求上传头像**（`GroupInfoServiceImpl:197` `null == avatarFile → CODE_1001`）。
   改了方向仍然跑不通。**我是在看到 `1001` 之后才去读源码的**——顺序反了：
   先读实现、再写探针，而不是先猜再验证。
3. **SQL fixture 连错 3 次列名**：`user_contact` 没有 `contact_name`（那是 `chat_session_user` 的）、
   `chat_session_user` 没有 `last_receive_time` 也没有 `contact_type`。
   本该先查 `information_schema` 再写 INSERT。
4. **门禁自身在这一轮出了 5 处断言粒度错误**，且**同一种错误犯了三次**：
   把「字面量内容类断言」（`X-Forwarded-For` / `','` / `"-"`）打在了
   `stripCommentsAndStrings` 处理过的文本上 → 字符串内容已被清空 → 恒红假失败。
   前两个门禁我已经踩过一次并写了注释提醒自己，这次还是踩了。
   **教训是「写过的教训」不等于「不会再犯」**——真正需要的是**机制**：
   把 `strip` 后的文本重命名为 `xxxClean`、原文命名为 `xxxRaw`，让误用在**代码评审层面**显而易见。
5. **门禁里写了一条假绿断言**：`IpTools.getClientIp` 出现位置 < `setIpAddress` 出现位置。
   实现是紧凑三元 `setIpAddress(cond ? IpTools.getClientIp() : x)` 时不成立；
   而 `IpTools` 完全缺失时下标为 `-1` 又会被误判为 PASS。
   与上一批 `verify_schema_drift.mjs` 的解析器自检是**同一类错误**：**用下标比较表达语义关系**。
   已改为解析 `setIpAddress` 的实参并检查是否含补齐调用（括号配平扫描，因实参内含方法调用）。

## 三、原因

1. **症状「全量失败 + 新代码刚落地」的组合会强烈诱导归因到新代码**。
   正确做法是先看失败是否覆盖了**与本次改动无关的路径**——
   本次连单聊都失败，而单聊根本不经过 `@所有人` 鉴权，这就该立刻指向「不是新逻辑」。
   我当时是靠日志而不是靠这个推理定性的，两者都该做。
2. **没有「先读实现再写探针」的纪律**。写冒烟探针时我依据的是「接口大概叫什么」的猜测，
   而仓库里 HTTP 端点命名与我的猜测有多处不符（`addGroup` vs `saveGroup`），
   方法签名（返回 Void / 强制 multipart）也完全没查。
3. **列名靠记忆**。这个仓库的 `user_contact` / `chat_session_user` 列集与直觉差异明显
   （`contact_name` 只存在于 `chat_session_user`，`user_contact` 用 `group_name`）。
   写 SQL 前查一次 `information_schema` 只需 1 条命令。
4. **「教训」只以注释形式存在于代码里，没有以机制形式约束**。注释对未来的我是可选阅读。
   真正能防住的是命名约定与统一工具函数。
5. **下标比较看起来简洁且在简单实现下恰好成立**。它在小改动下能工作，
   恰恰因此不容易在写的时候就发现它脆——直到实现被写成另一种等价写法。

## 四、改进方案

| 方案 | 落点 | 优先级 |
|------|------|--------|
| 门禁脚本统一命名约定：`xxxRaw`（原文，供字面量类断言）/ `xxxClean`（剥串剥注释，供实参类断言），并在两处各写一行用途注释 | 本轮新增的 3 个门禁脚本 | 立即 |
| 提供共享的 `callArgs()` / `methodBody()` 工具函数到 `scripts/verify/lib/`，禁止各脚本各写一份 | 后续门禁 | 中 |
| 冒烟脚本编写纪律：**先读 Controller 签名与 Service 实现再写探针**；不得凭接口名猜测 | `scripts/smoke/` 加统一头注释 | 中（立即写入本次 QA） |
| SQL fixture 前先跑 `information_schema` 取列名 | 同上 | 中 |
| 审计日志可查询性：管理端尚无「操作日志」页面（落库了但没人看得到） | 独立 Change（L4，管理端） | 中 |
| `at_user_ids` 未校验成员（可填任意 userId 导致多余红点） | 独立 Change | 低 |
| `X-Forwarded-For` 可信代理白名单 | 独立 Change（部署配置 L4） | 低 |

## 五、给下一批的经验

- **失败症状覆盖与本次改动无关的路径时，先怀疑环境与探针，而不是新代码**。本次连单聊都失败，
  而单聊不经过新逻辑——这个推理本该比读日志更快得出结论。日志与推理应当同时做。
- **门禁里的「下标比较」和「快照对比」都是隐性脆弱断言**。前者脆于实现写法变化，
  后者脆于「大家会去改快照绕过」。能用**解析结构 + 断言语义**表达的，不要用下标或快照。
- **同一个错误犯第二次，说明需要的是机制而不是注释**。
- **写冒烟探针的成本在「读源码」，不在「写请求」**。我三次改错都在这一侧。
