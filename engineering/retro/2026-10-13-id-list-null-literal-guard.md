# Retro — 名单解析器剔除「空值字面量」（遗留 #20 治本）

- 日期: 2026-10-13
- 关联 QA: `engineering/qa/2026-10-13-id-list-null-literal-guard.md`

## 做得好的

1. **拒绝了台账给的处置建议**。#20 原文写「若放宽空名单，必须先处理此脏值」。
   我去查了 per-moment 名单的实际来源（前端 `whiteSelected`，不是用户级那一列），
   发现**洗数据根本不解决隐患**——下次数据往返还会写回来。
   **台账里的处置建议本身是需要被验证的**，不能照做。
2. **「改用 id 形状白名单」这个更漂亮的方案被实测否决**。
   理由是既有测试用 `U001`（3 位）、生产用 `U` + 11 位，**两边都该放行**。
   如果只凭直觉实现，就会打破既有测试或误伤存量数据——而这条路径决定「谁能看到朋友圈」。
   **动手前先查既有测试用什么形态的 id**，这个动作救了这次改动。
3. **用等价变异如实登记第 3 处变异**。变异 3（调换两个判定的顺序）0 条转红，
   我没有把它记成「通过」，而是写明「`"null"` 被两判定各覆盖一次，顺序不影响结果」。

## 问题

1. **我差点下一个大错结论**。中途只看后端，发现 `momentVisibility` 只写不读，
   一度准备断言「整个朋友圈隐私特性失效」。查前端才发现 `PublishMoment.vue` 确实接线。
   **这正是 AGENTS §2.1 第 12 条警告的情形，而我在同一轮里差点犯。**
2. **常量放到了 class 体外**（import 之后、class 声明之前），编译报错
   「需要 class、interface、enum 或 record」。重读文件结构后才放对位置。
3. **两次 shell 引号/编码问题**（PowerShell 里 `<` 不支持重定向、`node -e` 里
   含引号的正则被吃掉），多花了两轮。

## 原因

1. **后端「只写不读」的证据太像缺陷了**。grep 出零调用就以为功能没接，
   忘了跨端接线可能落在前端——而本项目的隐私设置**正是**「后端存、前端读」的设计。
2. 编辑时没有先确认类的结构边界，import 之后就顺手写了。
3. 沿用了之前用过的命令形态，没重新验证 PowerShell 的支持情况。

## 改进方案

| # | 方案 | 落点 |
|---|---|---|
| 1 | **判定「特性是否失效」必须三端都查**（后端 grep / 前端 grep / spec Scenario），且**以 spec 的 Scenario 为线索先定位「这个功能声称在哪生效」** | 本次靠 `openspec/specs/privacy-settings` 的「打开发布页时以 …为初值」才定位到前端 |
| 2 | **改一个既有文件前先看它的结构边界**（class 体从哪开始），再决定插入点 | — |
| 3 | **台账里任何「应该先做 X 否则会 Y」的处置建议，接手时都要验证这个因果链**，而不是直接执行 | 本次验证结果直接推翻了原建议（洗数据不治本） |
| 4 | 改隐私/权限判定路径时，**先写清「行为恒等性证明表」再动手**（逐分支列出新旧结果对判定的影响） | 已写入 design.md ADR-005 与 spec Scenario |

## 下一步建议（未做，需人工决策）

本变更只堵了「空值字面量」这一类。若将来出现别的垃圾形态（如整列被写成
`"[object Object]"`、或编码损坏的 UTF-8 乱码），`parse` 仍会照样产出。
更彻底的方向是给 `parse` 前面加一层「能否解析为合法 JSON 数组」的探测，
但那会**放弃它刻意的宽松语义**（容忍无方括号的历史格式），属独立立项。
