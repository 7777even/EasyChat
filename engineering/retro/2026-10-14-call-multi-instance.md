# Retro — 后端通话支持多实例部署（call-multi-instance）

- 日期: 2026-10-14
- 效率等级: L4
- 关联 QA: `engineering/qa/2026-10-14-call-multi-instance.md`

## 做得好

1. **发现并订正了一条长期错误的系统事实**。台账原写「信令能跨实例是因为广播走 RTopic」——
   实测通话信令 `sendRawToUser` 只写本地 Netty ChannelGroup、房间 Map 进程内，**两层都缺口**。
   若不查就信，本 Change 会建在错误前提上。
2. **T8 主动判定「计划本身错了」而非照做**。design 写「广播断开事件让各实例清理本地状态」，
   前提是「有本地状态」；T6 删掉 `rooms`/`userCall` 后该前提消失。按 §2.1 第 12 条先穷举路径，
   结论是**不实现**，并同步修订 `spec-delta` 的 Requirement——**规格跟着事实走，不是事实迁就规格**。
3. **探针逼出了四次自我修正**，每次都指向真实盲区而非环境问题（见下「问题」2–5）。
4. **门禁的判定边界写清楚了**：`handleInvite` 函数体、先剥注释、Topic 名独立——
   避开「向上 N 字符经验窗口」这类会替相邻语句背书的写法。

## 问题

1. **T9 我把 `created` 变量声明删掉了，一度误判为「间歇性失败」。**
   真实原因是执行顺序：上一轮全绿的那次 `mvn test` 跑在我改坏**之前**，
   我把「旧结果」当成了「新代码的结果」。这不是环境抖动，是我对错了账。
2. **我写了一条 `&& true` 的假断言**（恒真，只为凑数）——正是 §2.1 第 3 条禁止的假装覆盖。
   发现后删除，并注明该语义由 `CallIdConflictTest` 的 `never().putMember` 行为断言兜住。
3. **探针改得不够彻底，我却先怀疑「门禁漏网」**：TTL 探针只删建房那两处 `expire`，
   而 `bindUser`/`touch` 里也有，门禁用的是子串断言 → 照样命中。
   **不是门禁失效，是探针没破坏到被判据覆盖的全部位置。**
4. **正则锚点连错三次**：`.expire` 要求在行首（实际是 `map.expire(...)`）；
   `\n\s*\.expire` 里 `\s` 吃掉 `\n` 导致要求两个换行；
   门禁里 `catch…createRoom…CODE_SYSTEM` 的**顺序**与实际代码 `try{createRoom}catch{CODE_SYSTEM}` 相反。
5. **`edit` 改类 javadoc 时把结构改坏**，残留一段重复且过时的注释，靠回读才发现（§2.1 第 11 条）。
6. **`tasks.md` 勾选框长期未回填**——进度一直只在会话里，收尾时才发现 0/16 被勾。
   §7 明确要求「任务状态只回填 tasks.md」，我违反了自己写的规则。
7. **★ 我把工作区弄脏了，然后差点把「自己造成的污染」当成产品缺陷查。**
   跑 `mutation_chat_dispatch.cjs` 时它把 `ChatMessage.vue` 的
   `v-if="data.status == 0"` 改成 `v-if="false"` **且未还原**，
   导致前端全量测试 785/786 恒红。我随后花了数轮排查这个「红」，
   一度准备按「产品骨架屏被硬关掉」立案——**直到 `git blame` 显示那一行是
   `00000000 (Not Committed Yet)`**，才意识到红的原因是**上一次跑变异没还原**。
   这是一条**自引用的假故障**：测试红 → 去查产品 → 产品没问题 → 查不出。

## 原因

- **对错账的根因是「并行了不该并行的事」**：改代码与跑验证之间没有建立「先改完再跑」的硬顺序，
  于是旧绿灯被读成新绿灯。这与「基线自检必须在最前」是同一族问题（§2.1 第 10 条③）。
- **假断言与不彻底探针的根因是「想让数字好看」**：7/7 比 6/7 更顺眼，
  于是用一条恒真断言凑数——但**数字好看恰恰让证据失效**。
- **先怀疑门禁而非怀疑自己的探针**：这是角色偏差。门禁是我写的，探针也是我写的，
  但我默认「探针是尺子、门禁是被测物」，而两者地位本该对等。
- **进度不回填的根因是「会话内有即时反馈就不想写文件」**——但会话不入仓，
  下一个接手的人看不到 7/16。
- **污染类假故障的根因是「门禁说了没做」**：`mutation_chat_dispatch.cjs` 注释写着
  「基线没通过就请先修好测试再谈判别力」，代码却只设 `exitCode=1` 就**直落探针循环**。
  于是基线红时它照跑变异、照报「9/9 捕获」，并把已被污染的文件当作 pristine 写回 ——
  **把污染固化**。16 个变异脚本里只有这一个有此缺陷（已逐个核对，非普遍问题）。

## 改进方案

1. **跑验证前先声明被验证的是哪个版本**：`mvn test` 前必须确认「本次改动已全部落盘」，
   输出里记录 commit/工作区状态，避免把旧绿灯当新绿灯。已适用于后续所有 L3/L4 收尾。
2. **探针也要过 §2.1 第 14 条**：变异必须破坏**判据覆盖的全部位置**（本例 TTL 有 5 处），
   只删一处时应由脚本检查「变异后该子串是否仍存在于别处」，存在即判 `[无效]` 而非 `[漏网]`。
   → 已在本 Change 的探针注释里写明；下个探针脚本应内置该自检。
3. **新断言先造反例（第 14 条），恒真断言零容忍**：写完 `check()` 先问「这条能不能恒真」，
   凡 `&& true`、无锚点、无作用域的直接删，宁可条数少。
4. **判定顺序固定为「先怀疑自己」**：探针 → 门禁 → 环境，逐层排除；
   输出必须区分 `[捕获]/[漏网]/[无效]`（本 Change 已做到，`[无效]` 正是靠它暴露探针不彻底）。
5. **tasks 勾选与代码同批提交**：每完成一层即回填一次勾选框，不留到收尾统一补。
6. **★ 变异脚本必须满足两条硬要求**（本 Change 实际修掉）：
   ① **基线自检失败立即中止**，不得继续跑探针（否则报的是红基线上的比大小）；
   ② **还原要验字节**，`调用过 restore()` ≠ `还原成功`。
   已在 `mutation_chat_dispatch.cjs` 补齐并用反例验证（污染基线 → 当场 `[致命]` 中止）。
7. **遇到「测试红但产品看着没问题」，第一步先 `git status` / `git blame`**，
   而不是去读产品逻辑。工作区状态是**成本最低的分歧点**，
   我这次绕了三轮才想到它——把它排到第一顺位。

# 补验 Retro（2026-10-21）— 双实例实跑

> 本节记录**交付之后**的补验（2026-10-21），不是 2026-10-14 那次的复盘。
> 起因：本机 Docker daemon 从「未运行」变为可用，于是当初登记为「未运行」的三项能做实了。

## 做得好

1. **「未验证」如实登记是对的，而且今天被证明有回报** —— 2026-10-14 交付时没有把
   单实例全绿包装成「多实例已支持」，所以今天的补验有明确的对比基准；
   若当时含糊收尾，今天连「该补什么」都要重新界定。
2. **补验自带反例对照** —— 正例（INVITE 送达）通过**且**反例（广播关闭后送不到）通过，
   两者成对才说明断言有判别力。反例里还额外断言「**房间仍已建在 Redis**」，
   否则「送不到」也可能是「服务端压根没处理」——那样反例没有区分力。
3. **每条断言都先证明前提成立**（LB 确实把两客户端分开、Redis 确实被阻塞），
   再看行为断言 —— 避免「什么都没测到却显示通过」。
4. **实测查出没人知道的 28s 失败反馈延迟**（Redisson 未显式配 `timeout`）——
   这条**只有实跑才暴露**，静态断言永远看不到。已登记为遗留 #35。

## 问题

1. **★ 交付时留了「做不成」的坑，却没留「怎么做」的路** ——
   README §4.7 写着「上线前请在真实 LB 环境做一次双实例通话冒烟」，**但没给任何工具**。
   下一个人要么重造一遍，要么干脆跳过。
2. **临时脚本没当场入库** —— 这次的 4 个冒烟脚本先在临时目录写，验证完才搬进仓库，
   过程中就已经出过两次「临时版本能跑、入库版本有语法错」的问题。
3. **`scripts/` 的性质被想当然** —— 差点把冒烟脚本混进 §10 门禁表；
   它们需要「双实例 + 活库」，进 CI 只会得到假信号，必须单列。
4. **我自己写的脚本自己踩了三个坑**：5060/5061 属 WHATWG 禁用端口（`fetch` 报 bad port）、
   `spawnSync`+`process.exit()` 触发 libuv 断言、房间是 HASH 类型却用 `GET` 判存在。
   每一个都白花了一轮。

## 原因

1. **「环境不具备」被当成了「不需要工具」** —— 交付时的判断是对的（当时确实没有双实例），
   但结论应当是「**做工具**」，而不是「**记一条未运行项**」。未运行项只解决了「不许吹牛」，
   没解决「下次怎么做」。
2. **临时目录是默认工作区** —— 我把临时目录当成了「先写再搬」的中转站，
   实际上它让「搬」这一步变成了纯体力活，还多出「搬完要重验」的成本。
3. **冒烟与门禁的界线没在动手前划** —— `scripts/verify/` 的既有形态让我下意识往里塞，
   直到写 README 才发现形态不匹配。

## 改进方案

1. **★ 交付「因环境受限而未验证」的能力时，必须同时交付工具** ——
   哪怕工具本身只能手动跑。「未运行项 + 工具」是一套，
   只登记未运行项等于把成本推给下一个人。
   本次已补：`scripts/smoke/`（4 脚本 + 种子 SQL + 用法 + 踩坑记录），README §4.7 直接指过去。
2. **工具入库要「先入库再验证」** —— 反过来（先在临时目录写、最后搬）会额外产生
   「搬完是否还跑得通」的二次成本，且临时目录还可能被清掉。
3. **冒烟与门禁的界线**：需要「多实例 / 活库 / 外部中间件」的 → 归 `scripts/smoke/`，
   **不进 §10 门禁表、不接 CI / pre-push**；纯静态可判的 → 才是 `scripts/verify/` 门禁。
4. **写跨进程脚本前先查协议细节**（禁用端口表、序列化类型、默认超时）——
   本次三个坑全是「以为是这样、实际不是那樣」，查一次源码/规范比试错快得多。
5. **实测发现的「延迟类」问题同样要登记** —— 帧到了不等于体验好；
   「不静默」和「及时」是两回事，台账里要分开记。
