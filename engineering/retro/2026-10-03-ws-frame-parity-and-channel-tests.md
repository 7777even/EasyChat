# Retro — WS 帧协议门禁 + ChannelContextUtils 单测

- 日期: 2026-10-03
- 分级: L2（补 2②-B 遗留）

## 一、做得好

1. **门禁先写、变异检验先跑，再修 bug**。发现 `case 25` 缺失后没有立刻去补一行 case，
   而是先把 parity 门禁写出来、让它自己报 ERROR。这既让门禁的判别力有个真实案例背书，
   也避免了我凭印象补 case（可能补错号）。
2. **门禁自动解析「落库白名单」而非人工维护第二份清单**。初版我打算在脚本里手写一份
   「哪些帧该有 case」的清单，很快意识到这是**同一事实的第二份拷贝**——
   和 2②-B 里 `parseList` 双解析器的漂移风险同源。改成从
   `ChatMessageServiceImpl` 的 `ArraysUtil.contains(new Integer[]{...})` 解析，
   人为维护面归零，改服务端即刻生效。
3. **把「已知缺口」显式登记而不是靠人记**。`KNOWN_GAP` 每次运行都打印，
   且**缺口被修好却没删登记时会阻断**——防止技术债登记表自身腐烂成摆设。
4. **变异检验暴露了我自己门禁的假绿**。首版把「解析不到落库白名单」当 WARN 跳过，
   变异 6 直接判 MISSED。这与 AGENTS §2.1 第 1 条同源：
   一个在结构漂移后永远绿的判据，比没有判据更危险。
5. **单测用真实 Netty `EmbeddedChannel` 而非 mock Channel**。
   最初用 `mock(Channel.class)` 塞进 `DefaultChannelGroup`，9 例直接 NPE——
   `DefaultChannelGroup.add` 内部会读 `channel.config()/pipeline()/allocator()`。
   换成 `EmbeddedChannel` 后，最后一例「开关不误伤消息投递」得以从
   `readOutbound()` 取真实帧逐字段校验，比打桩更有说服力。

## 二、问题

1. **首轮变异脚本全部 `exit=null` 且误判为「CAUGHT」**。
   `execFileSync('mvn', ...)` 在 Windows 上执行 `.cmd` 报 ENOENT，`e.status` 为 `null`，
   被 `!== 0` 判成捕获成功。**如果我不看具体失败用例名、只看汇总的 `[CAUGHT]`，
   就会带着一个「9/9 通过」的错误结论交付。**
2. **变异脚本的锚点三次未命中**（正则跨行/`\r\n` 不匹配），第一版有 2 例 `[SKIP]`。
   若不把 `[SKIP]` 计为「未捕获」，同样会得出虚假的「全部捕获」。
3. **两次把测试夹具当成了被测对象**。首版 `markOnline` 放**空** `ChannelGroup`，
   `isUserOnline` 判的是 `group != null && !group.isEmpty()`，于是 6 例全走离线分支失败。
   现象是「测试红了」，但根因是夹具错，不是实现错——这种时候如果直接去改
   `isUserOnline` 的实现，就会把测试改成迎合错误行为。
4. **发现位置消息 / 语音消息整条链路是断的**，且**必须靠 DB 实证才能确认**：
   代码上看是「wsClient 少个 case」，补完 case 才发现上游不落库、下游不渲染，
   三层都断。若只按「门禁报的 ERROR 修到门禁绿」就收工，会留下一个
   「门禁全绿但功能依然不可用」的状态。

## 三、原因

1. Node 的 `execFileSync` 在 Windows 上不解析 PATHEXT / 不经 shell，`.cmd` 不可直接执行；
   且异常路径下 `status` 为 `null` 而非非零数。这属于「环境假设未验证」。
2. 变异脚本用正则做锚点，而源文件是 CRLF 且中文注释夹在中间，正则没覆盖。
   更稳的做法是先用 `node -e` 打印锚点周边原文确认（第二次就是这么做的）。
3. 对 `ChannelContextUtils` 的静态 `USER_CONTEXT_MAP` 与 `isUserOnline` 语义理解不够，
   先写了「看起来对」的夹具。对**静态共享状态**的测试，夹具的正确性本身就是被测前提。
4. 门禁的「阻断条件」我只盯着「客户端 case 齐不齐」，没顺着数据流往上游追一步
   （服务端到底推不推这个帧、推之前落不落库）。**门禁报 ERROR 只说明症状，修症状不等于修根因。**

## 五、给下一批的经验

- **门禁报 ERROR 是症状，不是根因**。位置消息的门禁 ERROR 只是「客户端少个 case」，
  真根因在上游不落库、下游不渲染。修到门禁绿 ≠ 功能可用。
- **变异检验的价值一半在「证明门禁有效」，一半在「暴露门禁自身的假绿」**。
  本次它抓出了我门禁的假绿（解析失败被当 WARN 跳过）。
- **一个永远「通过」的判据比没有判据更危险**。汇总只看 `[CAUGHT]` 会被
  `exit=null` 骗过；必须逐例看失败用例名，且把 `[SKIP]` 计为失败。
- **测试红了先怀疑夹具**。静态共享状态 + 非空判断（如 `!group.isEmpty()`）
  是最容易写错夹具的地方，直接改实现等于把测试改成迎合错误行为。
- **门禁不要维护事实的第二份拷贝**。落库白名单从服务端源码解析，
  与 2②-B 把 `parseList` 抽成 `IdListTools` 是同一条经验。
- **DB 是功能的最后一任裁判**。`chat_message` 里 0 条 24/25 记录，
  是「这两个功能从未被真正使用过」最硬的证据——代码读得再仔细也不如这一条 SQL。
