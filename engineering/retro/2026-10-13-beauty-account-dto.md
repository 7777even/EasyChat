# Retro — 靓号保存端点改收 DTO（遗留 #31）

- 日期: 2026-10-13
- 关联 QA: `engineering/qa/2026-10-13-beauty-account-dto.md`

## 做得好的

1. **立项前先穷举，把「不是安全缺口」写在提案里**。台账原话是「违反 §3.6」，
   我没有直接接手，而是先查写入路径数、下游是否已校验、PO 有无可越权字段，
   得出「无跨用户越权」的结论，再据此把理由换成**结构性风险**
   （PO 加字段会被自动暴露为入参）。这让立项理由站得住，也避免制造安全恐慌。
2. **自己扫出全仓基数为 1**，而不是信台账「另一处」的措辞。扫 26 PO / 9 DTO / 28 Query
   × 全部 Controller，确认这是 §3.6 事实上的**唯一**违反点 —— 这句话后来成了 spec 的 Scenario。
3. **ADR 记录了「不做什么」比「做什么」多**：ADR-002（`status` 不加 `@NotNull`，
   否则新建即回归）、ADR-003（`id` 不加校验，不在两层各写一遍分流）、
   ADR-004（字段名保持同名故前端零改动）。这些「不做」最容易被后人「顺手优化」掉。
4. **变异 3 是自己加的**：前两个变异是「注解还在不在」，第三个改测
   「转换会不会漏字段」—— 这才是 ADR-001 选「逐字段手写」而非 `BeanUtils` 的**真正理由**，
   不测就等于 ADR 没兑现。

## 问题

1. **把「环境缺件」写成了行为断言**，初版多出一条恒红用例。
2. **凭空引用了 swagger 依赖**（`@Schema` / `@ApiModel`），本仓根本没有。
3. **反射 API 用错**：`getParameterAnnotations()[0]` 当 `Annotation[]` 用，编译失败。

## 原因

1. 我在**上一轮刚把 #32 登记过**（`standaloneSetup` 测不了方法参数约束），
   却还是在同一个测试文件里写了方法参数约束的行为断言 ——
   **知道的事没有即时应用到眼前这一行**。这是「台账只被写、不被读」的典型。
2. §3.6 的原文是「必须有中文注释 / `@Schema`」，我读到 `@Schema` 就**默认它可用**，
   没先 grep 确认依赖存在。规范里的「或」被读成了「且」。
3. `getParameterAnnotations()` 返回 `Annotation[][]`，
   我凭印象写成了降维后的单元素数组形式。

## 改进方案

| # | 方案 | 落点 |
|---|---|---|
| 1 | **写 MockMvc 测试前先问「这条约束的触发机制是什么」** —— DTO 字段级 + `@Valid` 走 `ModelAttributeMethodProcessor`（生效）；类级 `@Validated` + 方法参数注解走 `MethodValidationPostProcessor`（standaloneSetup 下不注册）。机制不同、结论相反 | 已写进本次测试类的注释与 spec Scenario |
| 2 | **规范里出现「或」时，两侧都要先核实存在性**（依赖是否引入、注解是否可用），再决定选哪一侧 | 已写入 DTO 注释 |
| 3 | 台账已有 #32 登记时，**凡写到相关测试文件，先重读该登记** | 本轮代价是一轮红→改→绿 |
| 4 | 反射断言尽量用**编译期可见**的写法；确需反射时先确认 API 的实际返回形状再写 | — |
