## 做得好的

- **验证先于结论**：守卫单测打在真实 `sqlite3` 层而非 mock 上，顺手 dump 了活体库结构，才挖出「两列根本不存在」这个比守卫本身更重要的根因 —— 若只测「不崩了」，会把**静默丢数据**当成修复完成。
- **L4 关卡没被吞掉**：发现结构变更需求时停下来问人工，拿到「现在补列」的明确指令后才动 `Tables.js`，符合前端 AGENTS §5。
- **测试脚本的失败被正确归因**：迁移测试首跑 2 个 FAIL，日志显示 SQL 已正确生成、`row:undefined`，判定为「测试只 update 未 insert」的脚本缺陷而非代码缺陷，补插入后 5/5 —— 没有为了凑绿去改产品代码。

## 问题

1. **四件套滞后于实现**：先写码后补 `proposal/design/tasks/spec-delta`，违反 §7.1「确认关卡完成后才允许写代码」的字面顺序。
2. **历史缺陷潜伏期长**：两列缺失从会话属性功能上线起就存在，期间「草稿不恢复」「免打扰丢失」一直被当作偶发体验问题，没人往表结构上查。
3. 测试入口必须用 esbuild 打包才能 import 主进程 ESM 模块（`ADB.js` 混用 `require` + `import`），每次验证多两步脚手架。

## 原因

1. L4 的判定发生在「已有 3 个文件在途修复」的延续会话里，我把注意力放在「把在途改动验证收尾」，补列是验证**过程中新发现**的，四件套被当成收尾动作而非前置动作 → 顺序倒置。
2. 本地 SQLite 是缓存层，字段缺失不报错：ADB 列映射静默过滤 + `insert`/`update` 均按 `columnsMap` 白名单拼 SQL，**任何字段缺失都表现为「写入成功但读不到」**，缺列从不抛异常，因此没有可观测的失败信号。
3. `ADB.js` 历史遗留双语法（CJS `require` + ESM `export`），只能被 electron-vite 打包消费，Node 直跑不了。

## 改进方案

- **结构类改动的四件套前置**：一旦判定触及 `Tables.js` / `easychat.sql`，立即先落 `proposal.md`（哪怕只有 Why+关卡），把「确认」这一步显式化，再动代码；本次 proposal 已在关卡处注明真实时序，避免文档伪造顺序。
- **把「缺列」纳入常规巡检**：新增一条轻量校验思路——对本地表做 `PRAGMA table_info` 与 Model 层写入键的差集断言（列映射里查不到 = 数据静默丢失），可挂进现有 smoke 脚本；下轮技术债择机落地。
- **验证脚本脚手架固化**：把「esbuild 打包 + `--external:sqlite3` + `NODE_ENV=development` 直连真实库」这套跑法写进 `scripts/verify/`，避免下次重推导。
