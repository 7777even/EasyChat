# Retro — 消除 Electron 打包配置双份

- Change: `openspec/changes/2026-10-06-electron-packaging-single-config/`
- 日期: 2026-10-06
- 等级: L4

## 一、做得好的

### 1. 用「实证」替代「文档记忆」，直接改变了对事实的判断

调查开始时我**断言**「`electron-builder.yml` 存在时会取代 `package.json` 的 `build`」，
并据此推断「mac 打包必然失败」。实跑日志打出
`loaded configuration file=package.json ("build" field)` 后，我去读了
`read-config-file/out/main.js:71-72`，结论**恰好相反**：
`packageMetadata[packageKey]` 存在即直接返回，`findAndReadConfig` **永不被调用**。

若我当时凭记忆落笔，会把方向写反，且这个错误会一路传播到 proposal / design / tasks。

### 2. 「死配置」这个真相比「配置写错」更值得挖

初判是「yml 里有 `build/entitlements.mac.plist` 但文件不存在」这类小问题。
顺着读下去才发现 **yml 自首个 commit（`a102bd9`）起就从未被读取过**，
而它表达的 `npmRebuild: false` 与 `files` 白名单两项意图**都造成了实际损失**
（打包超时、开发文件进包）。定位从「某个键错了」升级为「整份文件是死的」，
修复方式也随之从「补一个值」变成「消除双份配置」。

### 3. 主动设计「反向断言」，并因此抓到了自己的 bug

门禁里我加了「`files` 误排 `out/main/index.js` 等运行期必需文件 ⇒ 报红」。
正是这条断言让绿阶段**当场失败**，暴露出 `isExcluded` 把返回值写反了。

更关键的是后续：我用**「与 electron-builder 真实 `FileMatcher` 对拍 21 个探针」**
来验证自建的 glob 判定，又抓出**第二个反转条件**（跳过条件写成相等而非不等）。
这两处 bug 若没有对拍，会以「门禁全绿但结论与真实产物相反」的形式长期潜伏 ——
门禁全绿时，没人会怀疑门禁本身。

### 4. 两次自我纠正都留了痕

- 误判「原生模块 ABI 不匹配」：先扫 `node_modules` 得出 3 个「非 NAPI」包，
  差点报成风险。改按**生产依赖闭包**重算后只剩 `sqlite3`（`napi-v6`）。
- 误判「`files` 中止即全排除」：写成「首个命中即决定」，
  与真实的**交替状态机**（`minimatchAll`）不符。

两次都在同一个会话内发现并纠正，没有靠事后 review 兜底。

## 二、问题

| # | 问题 | 影响 |
|---|---|---|
| P1 | 门禁自建了一套 glob 语义，与 electron-builder 的 `minimatchAll` 存在漂移风险 | 高（门禁会给出与产物相反的结论，且全绿时无人察觉） |
| P2 | 连续三次在同一处（打包配置）才发现死配置，本可更早发现 | 中（一个从项目第一天就存在的死文件） |
| P3 | 中间那次 `--dir` exit=1 的失败原因（符号链接权限）与超时原因（重编依赖）**一度可能被混为一谈** | 中（会导致错误归因，进而错误地「修」环境而不是修配置） |
| P4 | 本机无法完成默认参数的完整打包，验证始终带一个 `-c.win.signAndEditExecutable=false` 缺口 | 中（exe 图标/元数据写入未验证） |
| **P5** | **首轮「验证产物存在」就宣称交付，未实跑启动 —— 自己引入的托盘图标回归因此漏过** | **高**（用户拿到的是启动即报错的包） |

## 三、原因

- **P1**：门禁必须**不依赖** `easychat-front/node_modules`（CI 的 `gates` job 不跑 `npm ci`），
  于是只能自己实现 glob。但「不重复实现」与「不引入依赖」在这里是冲突的，
  我选了后者，代价就是要额外建立对拍机制来保证等价 —— 而这个机制是**事后**补的，
  本该在写第一行 glob 之前就设计好。
- **P2**：死配置的**表现形式是静默的**（无警告、有一行不起眼的日志），
  而仓库里「文档/配置说一套、实际跑另一套」此前已多次发生
  （`orderBy` 门禁、`lint --fix`、变异脚本空转），
  我**没有**把「同类问题已复发」这件事当作应当优先排查打包配置的信号。
- **P3**：两次失败的**日志措辞差异大**（一个是 `rebuilding native dependencies`，
  一个是 `Cannot create symbolic link`），而我习惯性地用「上次也是失败」把它们并到一起。
- **P4**：本机环境限制（未启用开发者模式）客观存在，无法在本次消除。
- **P5（最严重）**：我在 design.md §6 里**亲手写下了**头号风险
  「`files` 白名单写过头 → 应用打出来却起不来」，并把它列为高概率风险，
  然后只用「4 个路径是否存在于 asar」去验证它。
  **风险陈述与验证手段不匹配**：我验证的是「我猜的那几个文件在不在」，
  而真正的失败模式是「我没想到的文件被排掉了」。
  更根本的是，我把「产物断言全绿」当成了交付充分条件，
  而**这类缺陷（读不到文件）恰恰只在运行期暴露**——
  且它表现为 `unhandled rejection`，**进程不退出，只看「活着没有」也查不出来**。

  讽刺的是，我写 design 时把这条风险标成「中概率 / 高影响」，
  却用了一个**证明不了它**的验证方式，然后据此宣称完成。
  这正是 AGENTS §2.1 第 12 条的精神：不能用局部证据推断系统行为 ——
  只不过这次我推断的是**自己的改动**。
