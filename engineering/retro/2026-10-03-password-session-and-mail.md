# Retro — 密码变更后会话失效 + 邮箱验证码真实投递

- Change: `openspec/changes/2026-10-03-password-session-and-mail/`
- 日期: 2026-10-03
- 分级: L4

## 一、做得好

1. **门禁先红后绿，且红得「对」**。`verify_password_session.mjs` 首次实跑 **9/29、exit=1**，24 项红全部对应真实缺陷。更关键的是**门禁自己出过两次假红并被抓出来修掉**：① 剥字符串把字面量内容也清了，导致 `value = "/login"`、`"rate_limit:"`、`"X-Forwarded-For"` 一律查不到——若没修，这 4 项会永远红，团队很快就会养成「这条门禁本来就有问题」的习惯从而忽略它；② 端点注解顺序是 `@PostMapping` 在**前**，我最初向**后**找 `@GlobalInterceptor`。**门禁的假红比假绿更有害**：假绿让人以为有防护，假红会让人拆掉防护。
2. **变异脚本改用沙箱副本，而非「改真文件 + 脏守卫」**。既有 `mutation_ws_frame_parity.cjs` 靠「工作区必须干净」的前置守卫保证还原安全——这意味着**交付中途（有未提交改动时）根本跑不了**。本脚本把门禁与其读取的 10 个文件复制到临时目录，门禁从副本位置解析 ROOT，天然只读沙箱。代价是要维护 `FILES` 清单，但换来「任何时候都能跑」。并额外加了「沙箱基线 == 真实基线」判定，防止清单遗漏导致「沙箱缺文件 → 门禁恒红 → 全部变异假通过」。
3. **对「恒绿用例」专门做了变异**。`resetPasswordByEmail_codeNotFound_doesNotInvalidateSessions` 在红灯态就是绿的——**恒绿即无判别力**。于是专门设计变异把吊销挪到方法开头，确认该用例转红。同理门禁的「fail-closed 是 throw 而非 log」最初只查 `CODE_1002` 是否出现，变异把 throw 换成 log 后仍能通过，遂补了措辞级锚定与「logger 不得接 code 实参」两条断言。
4. **失败路径的守卫用例写得比成功路径更细**。「改密失败不吊销」看着是次要需求，实际它防的是**任何人输错验证码就能把受害者踢下线**这个 DoS。把它写成显式守卫 + 变异证明，比只测成功路径有价值得多。
5. **零契约零 DDL 的范围自觉**。刻意不新增 `try_count` 列（ADR-005），把 DB 结构变更从「鉴权修复」里摘出去，使本批风险面收敛为「无 DDL、无接口破坏」，`check-api-contract --strict` 保持 0 漂移。
6. **纠正文档失真而非只追加**。发现 system-facts 里「修改密码…成功后关闭 WS 强制重登」记的是一个**从未实现**的行为。若只追加新事实，这条假陈述会继续误导后来人——**事实基线里一条不存在的安全行为，比没有文档更危险**。

## 二、问题

1. **活体冒烟第一轮 5 项红，全是我的探针端点选错**。`/userInfo/getUserInfo` 是 `@PostMapping`，我按惯例用了 GET，于是 405 → `code=1002`。**危险之处在于「对照组 B 不受影响」也是 1002**——如果我只看到「改密后旧 token 应返回 2001 却返回 1002」，很容易误判成「吊销逻辑把 B 也踢了」而去改生产代码。**是「对照项也失败」这个反常现象救了我**。
2. **T4 的红灯阶段被我跳过**。测试与实现几乎连写，事后才做 6 组变异补偿。这违反了 AGENTS §2.1-3 的「新增方法必须走完红阶段」。虽然最终有变异证据，但**变异只能证明「实现被破坏时会红」，不能替代「实现前测试确实会红」**——后者还顺带验证了测试的失败原因是否指向正确。
3. **变异过程中我自己造了个假信号**。第一次变异 `oldString` 吞掉了方法闭合大括号，导致编译失败；我看输出为空，一度以为「用例没判别力」，实为编译失败。**编译失败不是变异成功**——判变异结果必须同时看 `BUILD` 行，不能只看有没有 FAILURE。
4. **`GlobalOperationAspectTest` 首版有 2 处自身缺陷**。① lambda 内 `Class#getMethod` 抛受检异常 → 编译失败；② `rateLimit_withToken_usesTokenDimensionKey` 用了只标 `@GlobalInterceptor`（`checkRateLimit=false`）的端点，根本走不到限流分支——查证后发现**全仓 `checkRateLimit=true` 的 4 个端点全是 `checkLogin=false`**，token 维度分支只能靠「带旧 token 重登」触达。这条若不改，测试会给出一个虚假的覆盖感。
5. **PRD 级缺陷：`cleanUserTokenByUserId` 全仓零调用**。方法写好了、注释齐全、命名清晰，但**从未被调用**，也没人发现。这说明「实现完备」与「行为生效」是两件事——多端 Token 列表机制（`REDIS_KEY_WS_TOKEN_USERID_LIST`）在 `saveTokenUserInfoDto` 里有人写、有人用，唯独消费端空缺。

## 三、原因

1. **冒烟脚本靠「记忆中的接口语义」写，没有先核对注解**。仓库里 HTTP method 的历史遗留（`@RequestMapping` 不指定 method 逐步替换）使 GET/POST 不统一，凭直觉最容易出错。
2. **TDD 红阶段在「测试文件很大」时容易被跳过**。`MailServiceTest` 有 13 例、涉及 mock 装配与多个配置组合，写完已经很累，「再跑一次看它红」的动力下降。**但跳过的那一步恰恰是唯一能暴露「测试其实根本没在测东西」的时机**。
3. **变异脚本用「改真文件 + 脏守卫」这个模式，把「必须先提交」当成了前置条件**，于是最需要它的时刻（交付中途、代码刚改完）恰恰跑不了。
4. **`cleanUserTokenByUserId` 的零调用不是疏忽，是从未有人想过「改密后应该踢下线」**。安全需求没有被显式写进任何 spec 或测试，于是实现时无人把它当需求。**没有测试的安全需求等于不存在。**
5. 测试自身缺陷（问题 4）说明：**写鉴权测试时，「我以为的调用路径」和「代码真实走的路径」是两回事**，必须先用调试/断点或读码确认真实分支，而不是照着类名猜。

## 五、给下一批的经验

- **门禁和它自己的变异脚本都要「先红后绿」**：门禁先在未改造代码上跑红，变异脚本先在门禁为绿时跑。两者顺序反了，其中一方的结论就不可信。
- **变异结果的判读纪律**：`exit !== 0` 不等于「捕获成功」——命令没启动成功（ENOENT）与编译失败都会落到非零码，必须同时看输出内容与 `BUILD` 行。
- **测试里的「对照项」是最值钱的诊断信号**。「对照组也失败了」几乎总是测试自身或探针有错，而不是实现有错——先怀疑探针，再怀疑生产代码。
- **恒绿用例要专门做变异**。它可能是「本来就成立」的不变量，也可能是「什么都没断言」的摆设，两者只能靠变异区分。
- **事实基线里出现「本应存在却从未实现的行为」时，先把它当缺陷查证，再决定是改代码还是改文档**。本例中 system-facts 描述的强制下线行为是真实的 L4 漏洞。
