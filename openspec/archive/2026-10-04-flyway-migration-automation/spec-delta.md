> 与 proposal Capabilities 一一对应。

## ADDED Requirements

### Requirement: 迁移自动执行（对齐 Capability C1）

系统在应用启动时按编号顺序自动执行数据库迁移，已执行的跳过。

#### Scenario: 全新库从零执行全部迁移

- **WHEN** 对一个空库启动应用
- **THEN** 系统识别出仓库内全部迁移（当前 001~012），按编号顺序执行
- **AND** 执行失败时中止启动，不留下半成品状态

#### Scenario: 重复启动不重跑

- **WHEN** 应用在已迁移完成的库上再次启动
- **THEN** 已执行的迁移被跳过
- **AND** 不重复执行已应用的变更

#### Scenario: 迁移文件命名与位置约定保持不变

- **WHEN** 迁移文件位于仓库根、命名为 `easychat-migration-<NNN>-<描述>.sql`
- **THEN** 系统能直接识别（**零改名**）
- **AND** 该约定仍与项目规范一致

---

### Requirement: 迁移版本持久化记账（对齐 Capability C2）

每个库已应用的迁移版本被持久化记录，可查询。

#### Scenario: 版本表建立

- **WHEN** 迁移首次执行或存量库首次纳管
- **THEN** 库中出现迁移版本历史表，记录每个已应用迁移的编号、描述、校验和与执行时间

#### Scenario: 版本表不属业务基线

- **WHEN** 比对业务基线与活库结构
- **THEN** 版本历史表作为工具产物**不要求出现在业务基线中**
- **AND** 其存在只产生提示级差异，不阻断

---

### Requirement: 存量库纳管需先比对一致（对齐 Capability C3）

对没有版本历史的存量库，在纳管前必须先验证其结构与业务基线一致。

#### Scenario: 结构一致则允许纳管

- **WHEN** 存量库没有版本历史表，且其结构与业务基线**完全一致**
- **THEN** 允许纳管，把既有迁移视为已应用
- **AND** 输出醒目提示说明「已纳管，未重跑历史迁移」

#### Scenario: 结构不一致则拒绝启动

- **WHEN** 存量库没有版本历史表，且其结构与业务基线**存在差异**
- **THEN** **拒绝启动**并返回非 0 退出码
- **AND** 输出具体差异清单（基线有而活库没有的表 / 列、类型漂移）
- **AND** **不得**基于「假定已全部应用」而继续——假定正是历史上两次事故的成因

#### Scenario: 库为空或已有版本历史

- **WHEN** 库为空，或已有版本历史表
- **THEN** 直接放行，不做比对

---

### Requirement: 纳管版本号与迁移集同步（对齐 Capability C3 配套）

纳管所依据的版本号必须与仓库内迁移集保持一致。

#### Scenario: 新增迁移但未同步纳管版本号

- **WHEN** 仓库内迁移最大编号大于配置中的纳管版本号
- **THEN** 门禁**阻断**并报错
- **AND** 提示「新增迁移必须同步更新纳管版本号」
- **AND** 说明后果：存量库会把该新增迁移当作已应用而**静默跳过**

---

### Requirement: 迁移脚本不依赖客户端指令（对齐 Capability C4）

迁移脚本仅使用数据库通用 SQL，不使用 mysql 客户端专有指令。

#### Scenario: 迁移脚本不含 DELIMITER

- **WHEN** 任意迁移文件包含 `DELIMITER`
- **THEN** 门禁阻断
- **AND** 说明该指令是客户端专有、迁移工具无法解析，会导致全新库执行失败

#### Scenario: 迁移脚本不建存储过程

- **WHEN** 任意迁移文件包含 `CREATE PROCEDURE` / `CREATE FUNCTION` / `CREATE TRIGGER`
- **THEN** 门禁阻断

#### Scenario: 幂等加列的等价写法

- **WHEN** 迁移需要「列不存在才添加」
- **THEN** 使用条件判断 + 动态 SQL 执行
- **AND** **保持脚本可重复执行**（项目规范要求），而非依赖「只跑一次」的前提

---

### Requirement: 部署环境自动执行迁移（对齐 Capability C1 配套）

容器化环境下，迁移在应用启动前完成。

#### Scenario: 编排顺序

- **WHEN** 使用容器编排启动全套服务
- **THEN** 存在一次性的迁移执行步骤
- **AND** 应用服务在其**成功完成后**才启动（迁移失败则应用不启动）

---

## MODIFIED Requirements

### Requirement: 存量库迁移执行方式

存量库升级的迁移执行从「人工按编号顺序执行」改为「应用启动时自动执行」。

**变更前（引用现行 README §4.2）**：提示用户「存量库升级：按编号顺序执行未跑过的迁移脚本」，
逐个手工执行，且「哪些跑过」由人判断。

**变更后**：应用启动时自动识别并执行未应用的迁移；存量库首次纳管前先比对结构一致性。
人工逐个执行的路径保留（脚本仍幂等可重复执行），但不再是推荐路径。
