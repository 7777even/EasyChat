# Proposal — 名单解析器剔除「空值字面量」（遗留 #20 治本）

- 创建日期: 2026-10-13
- 效率等级: **L3**（改业务规则：朋友圈可见性判定路径上的名单解析）

## Why

`docs/system-facts.md` §14 遗留 #20 记载：活库 `user_info` 上存在字面量字符串
`"NULL"`（非 SQL NULL），台账给出的处置建议是「若将来放宽『允许空名单』，
**必须先处理此脏值**，否则白名单模式下无人可见」。

**2026-10-13 查证后该建议已被证伪，且真正的根因被找到了** —— 不是数据，是解析器。

### 真正的缺陷：`parse` 把「空值字面量」当成了用户 id

`IdListTools.parse` 用 `StringTools.isEmpty` 判空，而后者是：

```java
if (null == str || "".equals(str) || "null".equals(str) || "\u0000".equals(str)) {
```

**只认小写的 `"null"`**。于是：

| 输入 | `parse` 现状 | 应有 |
|---|---|---|
| `"null"` | `[]`（已覆盖） | `[]` |
| `"NULL"` | **`["NULL"]`** ✗ | `[]` |
| `"undefined"` / `"NaN"` / `"None"` | **`["NULL"]` 式的垃圾项** ✗ | `[]` |

活库里那条 `"NULL"` 正是这样一路走到界面上来的：任何新增的、直接解析名单列的读路径，
只要没有 JSON 前置守卫，都会拿到一个**含字面量 `"NULL"` 的白名单**。

### 为什么它「差一步」才出事

已核实的爆炸半径（活库 + 代码双向确认）：

- `moment.visible_list` / `invisible_list` 活库实测是**空字符串**，**没有**同样的脏值
  → 故 `canView` 当前**未**受影响；
- `user_info.moment_visible_list` / `moment_invisible_list` 全仓**从不参与任何判定**
  （只有 `requireFriendSubset` 在**写入口**解析用户输入），前端 `parseIdList` 遇
  非 JSON 会 `catch` 返回 `[]`；
- 故今天**没有用户能观测到**问题。

但隐患是**结构性**的：写入口有 `IdListTools.validate`（严格）把关，读入口靠 `parse`
（宽松）兜底，而宽松的那道口子恰好漏掉了大写变体。**任何将来新增的读路径都会踩中**。

### 为什么不是「洗数据」

台账建议「先洗数据再谈放宽」。查证后发现：**洗数据不解决这个隐患**——
脏数据只是**症状**，下次任何一次数据往返工具、或一个手滑的 SQL，都会重新写入。
而把解析器补上，脏数据是否还在都**不再产生错误 id**。

（用户本轮已明确选择「加解析守卫（治本）」，洗数据与门禁均未选择。）

## What Changes

- 后端:
  - `IdListTools.parse` 增加**空值字面量黑名单**（大小写不敏感），
    剔除 `null` / `undefined` / `nan` / `none`；
  - **不改变** `parse` 的宽松包络语义（仍容忍无方括号、缺引号）。
- 前端: 无改动。
- 数据库: **无变更**（不清洗现有那 1 行脏数据 —— 已证实当前无影响，且洗数据不治本）。
- 接口契约: 无变化。

## Capabilities

- C1: 名单解析**永不**把「空值字面量」当作用户 id 产出；
     隐私判定路径对脏输入的行为**与对空输入**完全一致

## Impact

- 对外接口: 无变化。
- 存量数据: 不动（现有 `"NULL"` 那行仍然存在，但已不会被解析成 id）。
- 性能: 无影响（一次 `HashSet` 查表）。
- 回退方案: 删除 `parse` 中的两行判定即可，无残留。
