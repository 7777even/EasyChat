# Proposal — 名单解析契约与实现对齐（`IdListTools.parse`）

- 创建日期: 2026-10-05
- 效率等级: **L3**（改动 `privacy-settings` 与 `at-all` 两个 capability 的共同依赖）

## Why

`IdListTools.parse` 的 **javadoc 声明与实际行为矛盾**（2026-10-04 补测时探针实测发现）：

```
javadoc：「剥 []、按 , 切分、剥 "、去重、**忽略空项**」
实测：   parse('[""]')                  → [""]              size=1
        parse('["U001","","U002"]')    → ["", U002, U001]  size=3
        parse('["U001","   ","U002"]')  → ["   ", U002, U001]  ← 空白元素整体成为「用户 id」
```

根因两处：
1. `StringTools.isEmpty("\"\"")` 为 **false**（长度 2、非空白）→ 空串元素进入集合，
   随后 `.replaceAll("\"", "")` 剥掉两个引号，**留下空串**；
2. 元素只做 `s.trim()` 后判空，**但 trim 结果未写回**，故 `"   "` 以 3 个空格成为一个 id。

**为什么必须修**：`IdListTools` 是「用户级隐私名单」与「单条动态可见范围」的**唯一真源**
（`MomentServiceImpl#canView` 已改为委托本类）。契约与实现不符的后果不是「当前就报错」，
而是**后续维护者据 javadoc 推理必错** —— 这是最难在评审与回归中发现的一类缺陷。

## What Changes

- 后端:
  - `IdListTools.parse`：`trim()` 结果写回；`trim()` 后为空的元素**跳过**（兑现 javadoc）
  - `IdListTools.validate`：`"   "` 这类纯空白元素**早已**被拒（实测），本轮对齐文档口径
  - `MAX_LENGTH` 与 `serialize` 语义**不变**
- 数据库: **无表结构变更、无迁移脚本**
- 接口契约: `extraData` / 名单列的**存储格式不变**（仍是 JSON 数组）

## Capabilities

- C1: `parse` 的行为与其文档承诺一致（忽略空项、元素被 trim）
- C2: 名单中的空串/空白项**不再被当作用户 id**
- C3: `validate` 与 `parse` 的空项口径一致（validate 拒、parse 忽略）

## Impact

- 对外接口: **无变更**
- **存量数据**: 需评估。若库中已存在含空串/空白项的名单列，修复后 `parse` 产出的**集合变小**
  （空项被丢弃）。**对可见性判定的实际影响**：
  - 空串/空白串**不可能等于任何真实 `userId`**，故黑/白名单的命中结果**不变**；
  - 唯一变化是 `MomentServiceImpl#canView` 的**遍历次数减少**（跳过无意义的比较）。
  → 结论：**无需数据迁移**，但需在 QA 中以活库查询证明「无名单列含空白项」或论证其无害。
- 行为变化: 修复前「`[""]` 解析出一个空串 id」，修复后解析为空列表
- 回滚方案: 单方法 revert，无数据迁移、无配置项
