# Design — 名单解析契约与实现对齐

- 关联 Proposal: `openspec/changes/2026-10-05-id-list-empty-item-contract/proposal.md`
- 创建日期: 2026-10-05

## 1. 缺陷的准确形态

```java
for (String s : arr) {
    if (!StringTools.isEmpty(s)) {                 // ← s 是含引号的原文，如 `""` 或 `  "  "`
        set.add(s.trim().replaceAll("\"", ""));    // ← trim 结果未写回；剥引号后可能留下空串/空白
    }
}
```

两处独立缺陷：

| 缺陷 | 输入 | 结果 | 根因 |
|---|---|---|---|
| D1 空串元素未被忽略 | `[""]` | `[""]`（size 1） | `isEmpty("\"\"")` = **false**（长度 2）→ 进入分支 → 剥引号后为空串 |
| D2 元素空白未 trim | `["   "]` | `["   "]`（size 1） | `s.trim()` 只用于判空，结果未回写 |

**注意 D2 的判空其实是对的**：`isEmpty("   ")` = true（`StringTools` 内部也 trim），
所以 `"   "` 是**直接跳过**的 —— 实测 `parse('["U001","   ","U002"]')` 得 size=3
（含一个 `"   "`）说明这一项**并没有**被跳过。根因是 `arr` 的切分方式：
`"[\"U001\",\"   \",\"U002\"]"` 剥括号后按 `,` 切分，第二段是 `"   "`（**含引号**），
`isEmpty("\"   \"")` = **false** → 进入分支 → trim 后 `"   "` → 剥引号 → `"   "`。

故 D1 与 D2 **同根**：判空作用于**未剥引号的原文**，而规范化（trim + 剥引号）在其后。
正确顺序是**先规范化、再判空**。

## 2. 与 `validate` 的口径对照

实测 `validate` **已经**拒绝这些输入（它走 fastjson 严格解析 + `instanceof String` + trim 判空）：

| 输入 | `validate` | `parse`（现状） | `parse`（修复后） |
|---|---|---|---|
| `[""]` | 拒 `CODE_1001` | `[""]` | `[]` |
| `["   "]` | 拒 `CODE_1001` | `["   "]` | `[]` |
| `[null]` | 拒 `CODE_1001` | `[]` | `[]` |
| `["", ""]` | 拒 `CODE_1001` | `[""]`（去重后 1） | `[]` |

即修复后 **`validate` 拒的一切，`parse` 都产出空** —— 读写口径对齐，
不会出现「写得进、读不出任何东西」的静默不一致。

## 3. 决策

### ADR-001：先规范化、再判空

- **决策**：`String norm = s.trim().replaceAll("\"", "").trim();` 然后 `if (!isEmpty(norm)) set.add(norm)`
- **理由**：一次修掉 D1 与 D2，且与 `validate` 的「trim 后判空」口径一致。
  两次 `trim()` 是必要的 —— `" \" \" "` 这类输入剥引号后仍可能带空白。
- **备选与否决理由**：
  - ❌ 只加 `if (norm.isEmpty()) continue` 但不写回 norm：D2 未修，空白 id 仍存在
  - ❌ 改用 fastjson 解析：`parse` 的**宽松语义是刻意的**（读存量脏数据必须容错，
    见 proposal Impact），换成严格解析会让历史脏数据直接抛异常，影响可见性判定

### ADR-002：不加数据迁移

- **决策**：不写迁移脚本
- **理由**：空串/空白串**不可能等于任何真实 `userId`**（用户 id 形如 `U01234567890`），
  故无论名单列是否含空白项，黑/白名单的**命中结果都不变**。
  唯一变化是 `canView` 遍历时少几次无意义比较。
  → 为一个「结果不变」的差异写迁移，等于凭空引入风险面。§6.4-2 的迁移要求针对的是
  **结构变更**，本变更不动 `easychat.sql`，故不适用。

### ADR-003：保留去重与顺序不保证

- **决策**：不动。内部仍用 `HashSet`
- **理由**：名单语义上是**集合**（黑名单/白名单），顺序无业务含义。
  改为保序会让测试与实现都更复杂，而收益为零。
  已在测试中显式声明「调用方不得依赖返回顺序」。

## 4. 数据影响

无表结构变更、无迁移脚本、无 `baseline-version` 变更。

**活库核查项**（QA 需执行或明确说明未执行）：查询名单列是否存在空白项。
涉及列：`user_setting` 的黑/白名单相关列、`moment.visible_list`、`moment.invisible_list`。

## 5. 风险

| 风险 | 评估 | 缓解 |
|------|------|------|
| 存量含空白项导致解析结果变小 | **低**，且不影响命中结果（ADR-002） | 测试显式覆盖该场景；QA 做活库核查 |
| `parse` 变严格导致某条链路抛异常 | **无** —— `parse` 本身**从不抛异常**（宽松是契约），修复后只会产出更小的集合 | 门禁断言 `parse` 对任意脏输入均不抛 |
| 有人误以为 `parse` 已变严格而移除容错 | 中 | 保留 ADR-002 说明与 javadoc 的「宽松」二字 |

## 6. 验证口径

- `IdListToolsTest`：新增/改写用例覆盖 D1、D2、`validate` 对照表
- 变异检验：① 去掉「规范化后判空」② 去掉第二次 trim → 用例必须转红
- 全量后端测试无新增失败
