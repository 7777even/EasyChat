# Spec Delta — 名单解析契约与实现对齐

- 目标 capability: `privacy-settings`（名单解析是该 capability 与 `at-all` 的共同依赖）
- 创建日期: 2026-10-05

## ADDED Requirements

### Requirement: 名单解析忽略规范化后为空的项

名单（黑名单 / 白名单 / 动态可见范围）的 JSON 数组解析，须**先规范化每个元素
（去首尾空白 → 剥引号 → 再去首尾空白），再判断是否为空**；规范化后为空的元素一律跳过。

#### Scenario: 空串元素被忽略

- **WHEN** 名单内容为 `[""]`
- **THEN** 解析结果为空列表
- **AND** **不**产出空串这一「用户 id」

#### Scenario: 纯空白元素被忽略

- **WHEN** 名单内容为 `["U001","   ","U002"]`
- **THEN** 解析结果为 `[U001, U002]`（2 项）
- **AND** 3 个空格的字符串**不**成为名单成员

#### Scenario: 剥引号后仍带空白也被忽略

- **WHEN** 名单内容为 `["  "]`（引号内含空格）
- **THEN** 解析结果为空列表

#### Scenario: 合法元素仍被正确解析

- **WHEN** 名单内容为 `["U001","U002"]`
- **THEN** 解析结果为 `[U001, U002]`
- **AND** 元素的**值**被去首尾空白（`[ " U001 " ]` → `U001`）

#### Scenario: 解析永不抛异常（宽松契约）

- **WHEN** 传入任意脏输入（非法 JSON、嵌套数组、纯文本、超长串、`null`）
- **THEN** `parse` 返回列表（可能为空），**不抛任何异常**
- **AND** 由调用方按业务规则决定如何处理空结果

> `parse` 用于**读取**可能含历史脏数据的名单列，故**宽松是刻意契约**；
> 严格校验由 `validate` 承担（写入侧）。本 Requirement 不改变这一分工。

---

### Requirement: 名单读写两侧的空项口径一致

`validate`（写入侧，拒绝脏数据）与 `parse`（读取侧，忽略脏数据）必须对「什么算空项」
给出**一致**的判断，不得出现「写得进、读不出任何东西」。

#### Scenario: validate 拒绝的输入，parse 一律产出空

- **WHEN** 名单内容为 `[""]` / `["   "]` / `[null]` / `["",""]`
- **THEN** `validate` 抛 `CODE_1001`
- **AND** `parse` 对同样输入返回空列表

#### Scenario: 合法名单两侧一致

- **WHEN** 名单内容为 `["U001","U002"]`
- **THEN** `validate` 通过
- **AND** `parse` 产出 2 项

## 已知边界

- **返回顺序不保证**：`parse` 内部用 `HashSet` 去重，输出顺序不稳定。
  调用方**不得**依赖顺序（名单语义是集合，顺序无业务含义）。
- **未做数据迁移**：修复后若存量名单列含空串/空白项，解析产出的集合会**变小**。
  但空串/空白串**不可能等于任何真实 `userId`**（形如 `U01234567890`），
  故黑/白名单的**命中结果不变**，可见性判定不受影响。详见 design.md ADR-002。
