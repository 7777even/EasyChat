# Proposal — 拆分被复用的通用错误码

- 创建日期: 2026-10-14
- 效率等级: **L4**（命中 §8「契约语义：`ResponseCodeEnum` 错误码分段与语义」）

## Why

`CODE_1001`（"请求参数错误"）在本仓**实际承载了 100+ 处、至少 8 类互不相同的语义**。它已经不是一个错误码，而是「失败了，看 `message` 吧」的兜底桶。

**实测清点（2026-10-14，`grep CODE_1001` 共 100+ 命中）**：

| 语义类别 | 代表来源 | 客户端需要的处理动作 |
|---|---|---|
| HTTP 绑定层失败 | 参数缺失 / 类型不匹配 / 方法不支持 / 媒体类型 / 请求体错误（`AGlobalExceptionHandlerController` 8 处）| 改输入 |
| Bean Validation | `@Valid` 各类约束 | 改输入 |
| **限流** | `GlobalOperationAspect#applyRateLimit` | **禁用按钮 + 倒计时**（与「改输入」完全不同）|
| **验证码过期 / 不正确** | `AccountController#validateCheckCode` 2 处 | **聚焦输入框 + 重置倒计时** |
| 业务规则校验 | 群组、朋友圈、敏感词、排序白名单、ID 列表、日期、邮件…（数十处）| 改输入 |
| 权限性校验 | 非接收方、非会话对方 | 改输入 |

**这带来的三个真实代价**（均可复现，非理论）：

1. **排障**：没有任何一个 code 能回答「这次失败属于哪一类」。监控与日志聚合只能靠正则匹配中文文案。
2. **测试**：自动化只能断言 `message` 文案。本仓**已因此反复踩坑** —— 本次会话的 TURN Change 里，
   T8 明确记录「限流与验证码共用 `CODE_1001`，导致只能断言文案不能断言码」。
3. **客户端**：限流与验证码失败当前走的是**和「参数填错」完全相同**的 Toast 分支，
   用户只被告知「请求过于频繁，请稍后再试」，既没有倒计时也无法聚焦重输。

## What Changes

**只拆「客户端需要特殊处理 + 监控需要单独告警」的两类；其余保持 `CODE_1001`。**

- 后端:
  - `ResponseCodeEnum` 新增两码（落在**通用段 1000-1999** 内，符合 §3.1）：
    `CODE_1004`（请求过于频繁）、`CODE_1005`（验证码错误或过期）。
  - `GlobalOperationAspect#applyRateLimit` 改抛 `CODE_1004`。
  - `AccountController#validateCheckCode` 两处改抛 `CODE_1005`。
  - **其余 90+ 处调用点一律不动**（含 `BusinessException` 的两个无参构造默认码）。
- 前端:
  - `Request.js` 的 `ErrorCode` 枚举同步两码，并**真正使用**（当前 `PARAM_ERROR: 1001` 是定义了从未用）。
  - `Request.js` 对 `CODE_1004` 做特殊处理：**透传结构化信息**（剩余窗口秒数），由调用方决定是否禁用按钮；
    未提供时维持现状（普通 Toast），**保证向后兼容**。
- 数据库: **无变更**。

### 明确不做（避免范围扩散）

- **不**逐个给 90+ 处业务校验重新归类。它们同属「你的输入有问题」，用户处理方式一致；
  拆开只增加维护面而不产生用户价值。
- **不**加 `category` 之类的额外响应字段（避免契约膨胀）。
- **不**改 HTTP Status 语义（`Result` 包络与 `code` 保持现状）。

## Capabilities

- **C1**：限流有独立错误码，客户端可据此做**倒计时/禁用**，监控可对刷接口**单独告警**。
- **C2**：验证码失败有独立错误码，客户端可**聚焦输入框并重置倒计时**。
- **C3**：错误码**分段与前后端同步**由门禁锁住 —— 新码必须落在 `1000-1999`，
  且前端枚举与后端枚举**双向对账**（防漂移，这正是本次发现问题的根因之一：`PARAM_ERROR` 定义了却没用）。

## Impact

- **对外接口**: **响应结构不变**（仍是 `Result{code,message,data}`），
  但 **`code` 取值集合新增两个**。→ 属契约变更，命中 §8 L4。
- **存量数据**: 无影响。
- **性能 / 安全**: 无性能影响；安全上是**正向**——验证码错误独立后可单独告警，便于发现撞库。
- **兼容性**:
  - 老版本客户端不认新码 → 会落到「其他错误」分支 → **照常 Toast 展示 `message`**，行为不变。**向后兼容。**
  - 新版本客户端不认老码 → 同理。故**前后端可任意顺序发布**。
- **回退方案**: 把两处调用点改回 `CODE_1001` 即可，**无数据迁移、无接口结构变更**，回退成本极低。

## 需你知悉的判断（我已核实，但影响取舍）

1. **改码本身对用户体验零变化** —— 已实测前端 `Request.js` 响应拦截器只认 `0` / `2001` / 其他，
   `ErrorCode.PARAM_ERROR: 1001` **定义了从未使用**。所以本 Change 的价值**不在改码本身，
   而在于「改码 + 客户端利用 + 门禁锁住」三件套**。若只改码不改客户端与门禁，则纯属无效改动。
2. **向后兼容已确认**：老客户端不认新码时落到默认 Toast 分支，行为与现在一致。
3. **不拆其余 90+ 处是刻意的**：它们用户处理方式相同；全量拆分会大幅放大回归面而收益甚微。
   若你希望「一次到位、全量归类」，请在关卡处说明 —— 那是**另一个规模**的改动（预计 10 倍工作量）。
