# Proposal — 敏感词替换改为「长词优先」使打码结果与词表顺序无关

- 创建日期: 2026-10-05
- 效率等级: L3（改业务行为：同一内容的打码输出会变化）
- 台账对应: `docs/system-facts.md` §14 遗留 **#22**

## Why

`SensitiveWordServiceImpl#filter` 第二遍用 `result.replace(word, "***")` **逐词替换**，遍历顺序即 `wordList` 的顺序；而 `SensitiveWordMapper.xml` 的 `selectByStatus` **没有 `ORDER BY`**，故顺序由 DB 决定且 `reload()` 后可能变化。

后果：短词若排在长词之前，先被替换成 `***`，长词随即失去匹配机会 —— 词表 `["ab","abcd"]` + 内容 `"abcd"` 得 `***cd`（`cd` 残留），词表反序则得 `***`。**同一份词表在不同环境 / 不同次 `reload()` 后打码结果不同**，出问题无法复现、无法归因。

这与 AGENTS §2.1 第 12 条要求的「可复现」背道而驰：审核结果必须是**词表内容的纯函数**，而不是词表行顺序的函数。

## What Changes

- 后端:
  - `service/impl/SensitiveWordServiceImpl`：`reload()` 额外预计算一份**按词长降序**的替换用列表（`maskingList`）；`filter` 第二遍改遍历该列表。第一遍（level=3 拦截）**不动**。
  - `entity/po/SensitiveWord`：不改。
  - `SensitiveWordMapper.xml`：**不改**（顺序无关性由 Service 侧保证，不必把排序下推到 SQL —— 那样每次 `reload()` 多一次 filesort，且语义分散在两层）。
- 前端: 不涉及。
- 数据库: **无表结构 / 字段变更**（故不升 L4）。

## Capabilities

- C1: **打码结果与词表顺序无关** —— 给定同一份词条集合，任意排列下 `filter` 输出**逐字节相同**。
- C2: **长词优先命中** —— 存在包含关系时，优先替换更长的词，短词在长词已消失后不再命中。
- C3: **level=3 拦截语义完全不变** —— 仍以**原始未替换内容**、与词表顺序无关地判定（第一遍不动即天然满足）。
- C4: **性能不退化** —— 排序在 `reload()` 内一次性完成，`filter` 热路径仍是 O(词数) 线性扫描，不引入每次调用的排序开销。

## Impact

- 对外接口: **不变**。`filter` 签名与返回类型不变，仅特定输入（词表含互相包含的词）下的**输出字符串**变化。
- 存量数据: **不需迁移**。活库实测 `sensitive_word` 9 条（level 2×4、level 3×5），**互相包含的词对 = 0**，即当前线上输出**逐条不变**；修复只对未来新增的包含关系词表生效。
- 性能 / 安全:
  - 性能：`reload()` 每次多一次 O(n log n) 排序（n = 词条数，量级几十），`filter` 热路径不变 → **无影响**。
  - 安全：**方向是收紧**（`***cd` → `***`，残留片段减少），不存在放松方向。
- 回退方案: 单文件回退 `SensitiveWordServiceImpl` 即可，无数据 / 无 schema 变更需要逆向操作。
- **测试影响**: 现有 `SensitiveWordFilterTest#maskingIsOrderDependent` **锁定的是缺陷行为**（`assertEquals("***cd", a)`），必须随本次修复改写为「顺序无关」断言 —— 它记录的是缺陷现象，不是契约。
