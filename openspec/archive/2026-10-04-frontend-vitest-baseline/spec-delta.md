## ADDED Requirements

### Requirement: 渲染层组件具备可运行的自动化测试（对齐 Capability C1）

前端渲染层组件具备可复现的自动化测试命令，测试失败时命令以非 0 退出码结束。

#### Scenario: 测试命令可复现

- **WHEN** 开发者执行 `npm run test`
- **THEN** 渲染层组件测试被执行
- **AND** 全部通过时退出码为 0

#### Scenario: 测试失败时命令以非 0 退出

- **WHEN** 任一测试用例失败
- **THEN** `npm run test` 以**非 0** 退出码结束
- **AND** 失败用例被明确指出（不得静默通过）

#### Scenario: 测试基建本身先被验证可运行

- **WHEN** 首次接入测试运行器
- **THEN** 必须先用一个**故意失败**的用例确认命令能转红并返回非 0 退出码
- **AND** 未确认该步骤前不写入正式用例

---

### Requirement: 测试基建零生产依赖（对齐 Capability C2）

测试基建仅存在于开发依赖中，不进入生产依赖、不影响打包产物。

#### Scenario: 新增依赖全部为开发依赖

- **WHEN** 引入测试运行器与组件测试工具
- **THEN** 它们只出现在开发依赖段
- **AND** 生产依赖段**零变更**

#### Scenario: 构建工具链版本不被顺带升级

- **WHEN** 引入测试运行器
- **THEN** 既有构建工具链（打包器与前端构建器）版本**不被连带升级**
- **AND** 若被连带升级，门禁阻断并要求改用兼容版本

#### Scenario: 依赖版本钉死

- **WHEN** 查阅开发依赖声明
- **THEN** 测试相关依赖使用**精确版本号**
- **AND** 不使用范围前缀（否则某天自动升级会破坏构建）

---

### Requirement: 测试纳入持续集成（对齐 Capability C3）

组件测试在持续集成中作为门禁执行，测试失败导致流水线失败。

#### Scenario: 前端流水线执行组件测试

- **WHEN** 前端流水线运行
- **THEN** 组件测试被执行
- **AND** 测试失败则该流水线失败

#### Scenario: 测试基线有专属门禁守护

- **WHEN** 测试基建被改动或破坏
- **THEN** 门禁能发现「测试运行器版本被顺带升级」「别名两处不一致」
      「必要的全局桩缺失」「生产依赖被测试框架污染」等偏离
- **AND** 该门禁经变异检验确认会转红

---

### Requirement: 测试环境与生产渲染环境隔离（对齐 Capability C4）

组件测试在与生产渲染等价的 DOM 环境中运行，但不得访问真实主进程能力。

#### Scenario: 提供 DOM 环境

- **WHEN** 运行组件测试
- **THEN** 提供完整的文档对象模型环境
- **AND** 提供渲染层依赖的浏览器能力（尺寸观察器、交叉观察器、媒体查询）

#### Scenario: 主进程桥接被拦截

- **WHEN** 组件在测试中调用主进程桥接方法
- **THEN** 调用被桩函数记录而不真正执行
- **AND** 不访问真实文件系统、网络或数据库

#### Scenario: 依赖浏览器能力的能力缺失时可挂载

- **WHEN** 组件依赖尺寸观察器等浏览器能力
- **THEN** 测试环境提供该能力的桩，使组件可以完成挂载
- **AND** 缺少该桩时门禁阻断

---

### Requirement: 测试锁定已知的静默失效点（对齐 Capability C5）

首批组件测试针对历史上真实发生过的「条件漏项导致不渲染、不报错」缺陷。

#### Scenario: 消息类型到渲染组件的映射被断言

- **WHEN** 给出某个消息类型
- **THEN** 系统渲染出该类型对应的消息组件
- **AND** 断言覆盖全部已支持类型，而非抽样

#### Scenario: 未支持的消息类型不渲染消息组件

- **WHEN** 给出未被支持的消息类型
- **THEN** 不渲染任何消息组件
- **AND** 该行为不产生异常

#### Scenario: 前端覆盖类型与后端类型枚举对账

- **WHEN** 后端新增了需要前端渲染的消息类型
- **THEN** 前端分发条件未覆盖该类型时，测试**失败**
- **AND** 提示该类型未被任何渲染分支处理
- **AND** 该摩擦为**有意保留**：漏一个类型的表现是「消息拉到却什么都不显示」，无异常无日志

#### Scenario: 二次分发同样被覆盖

- **WHEN** 某消息类型由父组件分发到子组件后还需再次分发
- **THEN** 二次分发路径同样有断言
- **AND** 断言其渲染出具体子组件，而非断言「没报错」

## MODIFIED Requirements

### Requirement: 前端逻辑的自动化验证方式

前端逻辑的自动化验证从「仅纯核心的脚本校验」扩展为「纯核心脚本校验 + 组件测试」。

**变更前**：前端仅 `verify_*_core.mjs` 一类脚本校验，且只覆盖**不依赖框架的纯逻辑核心**
（导出格式化、通话帧转移、通话状态机、虚拟列表算法）。组件层无任何自动化验证。

**变更后**：在保留脚本校验的基础上，新增组件级测试覆盖渲染层分发逻辑。
两类手段**互补而非替代**：脚本校验适合纯函数（快、无环境依赖），
组件测试适合条件分发与渲染分支（必须挂载）。
