# Design — 邮箱验证码失败次数限制

## 架构

```
POST /account/resetPassword          ← 契约不变
   │
   ▼  @GlobalInterceptor(checkRateLimit=true, rateLimitByParam="email")   ← 上一轮已加
   │   60 次 / 分（按 email 维度）
   ▼
AccountController#resetPassword(@Valid UserResetPasswordDTO)
   ▼
UserInfoServiceImpl#resetPasswordByEmail(email, code, newPassword)
   │
   ├─【新增】isEmailCodeLocked(email)          ── Redis GET ──► 超限? 抛 CODE_1001
   │
   ├─ 原有：查未使用的 type=1 码
   │     ├─ 空 →【新增】recordEmailCodeFailure(email)  ── Redis INCR + EXPIRE ──► 抛「验证码错误」
   │     ├─ 过期 → 抛「验证码已过期」        ← 刻意**不计数**，见 ADR-002
   │     └─ 继续 …
   │
   ├─ 用户不存在 → 抛 CODE_2101               ← 刻意**不计数**，见 ADR-002
   │
   ├─【新增】clearEmailCodeFailure(email)    ── Redis DELETE ──►
   └─ 改密码 / 标记码已用 / 吊销全部端 Token（原有流程，一字未改）
```

## 决策（ADR）

### ADR-001: 计数放在 Redis 键 `easychat:emailcode:fail:{email}`

| 方案 | 粒度 | 攻击者能否绕过 | 成本 |
|---|---|---|---|
| A. DB 加 `fail_count` 列 | **每个验证码行** N 次 | **能** —— 每 60 秒重发新码即获得新的 N 次额度，10 分钟内约 10 码 × N | 迁移脚本 + `easychat.sql` + Mapper XML 三处 + bump `baseline-version`（**L4**） |
| **B. Redis 按 email 累计**（选中） | **每邮箱每窗口 N 次**，跨码累计 | **不能** —— 重发新码不重置计数 | 3 行代码 + 2 个常量 |

**选 B**。A 的粒度正是它的致命处：限流若可被「重发验证码」这个**受害者无法阻止**
的动作重置，就等于没有。而 B 只需 60 秒 TTL 的内存计数。

**代价**：Redis 数据丢失 / 重启会清零计数。这是**可接受**的——本仓的端点限流
（`applyRateLimit`）本就以 Redis 为准，**同一故障域**不会造成「限流失效但失败计数也失效」
之外的新不一致。

### ADR-002: 只在「验证码不存在」时计数，**过期**与**用户不存在**不计数

三条早退路径里，只有第一条是暴力破解的特征：

| 路径 | 是否计数 | 理由 |
|---|---|---|
| `list.isEmpty()`（码不存在 = **猜错了**） | **计数** | 暴力破解**唯一**会走到的分支；不限它等于不限暴力破解 |
| 码已过期 | **不计数** | 此时无可猜的目标。若计数，攻击者只需在验证码过期后发 5 次垃圾即可**永久锁死受害者**——把限流变成了更严重的 DoS |
| 用户不存在（`CODE_2101`） | **不计数** | type=1 的码只可能发给已注册邮箱，故此分支实际只在「发码后账号被删」时出现；计入会把罕见状态当攻击信号 |

**这是本 Change 最重要的取舍**：宁可漏计两条分支，也不要让限流本身成为 DoS 放大器。

### ADR-003: 锁定检查放在 DB 查询**之前**

`isEmailCodeLocked` 是一次 Redis `GET`，比 `emailVerifyCodeMapper.selectList` 便宜得多。
放在最前面意味着**攻击流量在 Redis 层就被挡掉，不会打到 MySQL**。
代价：锁定状态下仍会产生一次 Redis 读（可忽略）。

### ADR-004: 接受「可锁死受害者」，但把窗口压到与验证码同寿命

任何基于次数的验证码限流都有这个面。本 Change 的缓解：
- 窗口 = **10 分钟**，与验证码寿命一致 —— 被锁住的时间**不会超过**验证码本身的可用时间；
- 受害者仍可**正常收到**新验证码（`sendEmailCode` 不受影响），只是暂时用不了；
- 窗口过后自动恢复，无需人工介入。

**显式登记为已知取舍**（写入 spec 的「已知边界」），不假装没有。

### ADR-005: 计数键只含 email，**不含 type**

`resetPasswordByEmail` 只消费 `type=1`，单一消费者，加 `type` 维度是无效复杂度。
（若将来 type=2「修改邮箱」也走同一路径，届时再拆键 —— 那时是两个独立的攻击面，
混在一个键里反而会让其中一个的类型拖累另一个。）

### ADR-006: 超限文案**说明恢复时间**，但**不泄露**此前失败了几次

「验证码错误次数过多，请 10 分钟后再试」让合法用户知道该怎么做；
不报具体次数，避免给攻击者一个精确的进度反馈（差 1 次 vs 差 4 次）。

**未失败时维持既有文案**（「验证码错误」/「验证码已过期」/ `CODE_2101`）**一个都不改** ——
本 Change 不引入任何新的用户枚举面。

### ADR-007: 成功验证时清零，**发码时不清零**

- **成功时清零**：否则用户一次成功后，下次找密码会被上一次的陈旧计数挡住。
- **发码时不清零**：清了就等于给了攻击者「重置额度」的开关（ADR-001 的整个理由）。

## 风险

| 风险 | 缓解 |
|---|---|
| 攻击者锁死受害者（ADR-004） | 窗口与码同寿命；写进 spec「已知边界」；不把过期/不存在计入计数以免永久锁 |
| Redis 不可用时行为退化 | 与端点限流同一故障域：`RedisUtils` 返回 `null` 时按「未超限」处理（fail-open），理由与 `applyRateLimit` 一致 |
| 阈值 / 窗口散落成字面量 | 提为 `Constants` 常量，单测直接对齐，不写魔法数字 |
| 既有 6 例 `resetPasswordByEmail` 测试需重写 | 它们都走「码存在」或「码为空」路径，前者新增一次 Redis delete（mock 下无副作用），后者需 mock `incr` 返回值。**这是预期的**，不是破坏 |

## 依赖

**零新依赖**。注入既有 `RedisUtils` Bean。

## 数据影响

**零**。不写库结构、不改字段、不迁移数据。
「DB 加列必须改满三处」不适用——本 Change 不动表。
