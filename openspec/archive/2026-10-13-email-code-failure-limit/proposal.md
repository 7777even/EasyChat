# Proposal — 邮箱验证码失败次数限制（遗留 #1 根治）

- 创建日期: 2026-10-13
- 效率等级: **L3**（原判 L4，**经查证修正**，见下）

## ⚠️ 效率等级修正说明

立项时本项被标为 **L4（含迁移脚本）**，理由是「失败次数需要持久化，须给
`email_verify_code` 加 `fail_count` 列」。**该前提经查证不成立**：

- `RedisUtils` 已有 `incr` / `expire` / `delete` / `get`（与 `GlobalOperationAspect`
  的 `applyRateLimit` 同一套机制），失败计数**完全不必落库**；
- `RedisComponet` 虽是业务语义封装（无 `incr`），但注入 `RedisUtils` 即可，不引入新依赖。

故实际等级为 **L3**：无表结构变更、无迁移脚本、不动 `easychat.sql`、
不 bump `baseline-version`。**数据库结构是 L4 的触发条件之一（AGENTS §8），
本变更不触碰它。**

## Why

`docs/system-facts.md` §14 遗留 #1 的落点列写着「**已解决（部分）**」，
并明确留下残余风险：

> **残余风险（仍开放）**：无失败次数限制，单次命中 10⁻⁶、有效期 10 分钟；
> 攻击者对**同一邮箱**的尝试被限到 60 次/分，但可**换邮箱**。
> 跨邮箱的分布式尝试仍无约束，若需根治须加 `email+code` 维度失败计数字段（L4，含迁移脚本）

### 查证后的真实攻击面（不引用台账措辞，自己重算）

| 事实 | 值 | 出处 |
|---|---|---|
| 验证码位数 / 空间 | 6 位 / **10⁶** | `StringTools.getRandomNumber(Constants.LENGTH_6)` |
| 有效期 | **10 分钟** | `expireTime = now + 10*60*1000` |
| 端点限流 | **60 次/分**（按 email 维度，遗留 #1 上一轮引入） | `RATE_LIMIT_PER_MINUTE` |
| **单邮箱 10 分钟内可尝试** | 60 × 10 = **600 次** | 上两行相乘 |
| **命中概率** | 600 / 10⁶ = **0.06%** | |

**「可换邮箱」其实不成立**——需读完整条链路才看得出：

- `resetPasswordByEmail` 在校验通过后查 `userInfoMapper.selectByEmail(email)`，
  **用户不存在直接抛 `CODE_2101`**（`UserInfoServiceImpl:508-510`）；
- 而 `sendEmailCode` 对 `type==1`（找回密码）同样要求用户已存在，否则抛 `2101`
  （`:446-449`）——即**未注册邮箱根本不会有 type=1 的有效码**。

所以攻击者**只能瞄准已注册邮箱**，无法靠换邮箱把成本摊薄。这是原台账措辞的一处
**高估风险**，本 Change 据实修正。

### 为什么 0.06% 仍要修

它不是「大漏洞」，是**概率性凭证重置**——命中即等于账号被接管，
且没有任何告警。0.06% 听起来低，但它是**可重复**的：
攻击者对 N 个目标各试 600 次，累计命中率随目标数线性上升。

### 一个必须承认的取舍：锁死受害者

限流必然带 DoS 面：任何人只要知道某邮箱，就能用 5 次错误尝试把该邮箱锁 10 分钟
（受害者无法使用新收到的验证码）。这是**所有**验证码失败计数的固有代价
（GitHub / Google 均如此），本 Change 选择接受并在 spec 中显式登记，
而不是假装没有。缓解见 design.md ADR-004。

## What Changes

- 后端:
  - `UserInfoServiceImpl#resetPasswordByEmail` 增加失败计数与锁定判定；
  - 新增 `Constants.REDIS_KEY_EMAIL_CODE_FAIL` 前缀与 `EMAIL_CODE_FAIL_MAX`（=5）
    / `EMAIL_CODE_FAIL_WINDOW_SECONDS`（=600）两个常量；
  - 注入 `RedisUtils`（既有 Bean，**非新依赖**）。
- 前端: 无改动（错误文案走既有 `Result.fail` 通道）。
- 数据库: **无变更**。
- 接口契约: 路径 / 方法 / 参数**全部不变**；**响应文案新增一类**
  —— 计数超限时返回 `CODE_1001` + 「验证码错误次数过多，请 N 分钟后再试」。

## Capabilities

- C1: 邮箱验证码的**错误尝试次数**有上界，且上界**跨验证码累计**，
     攻击者重发新码无法重置计数

## Impact

- 对外接口: **不变**（除新增一类拒绝文案）。
- 存量数据: 无影响（计数只在 Redis，不写库）。
- 性能: 每次重置多 1~2 次 Redis 操作（`get` / `incr`+`expire`），可忽略。
- 回退方案: 移除 `resetPasswordByEmail` 中新增的三个方法调用即可，
  计数键会自然过期，无需清理。
