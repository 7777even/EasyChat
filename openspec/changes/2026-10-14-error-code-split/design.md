# Design — 拆分被复用的通用错误码

- 关联 Proposal: `2026-10-14-error-code-split/proposal.md`
- 创建日期: 2026-10-14
- 效率等级: **L4**

## 1. 现状事实（2026-10-14 实测，非推断）

| 事实 | 证据 |
|---|---|
| `CODE_1001` 有 **100+ 处**调用点 | `grep CODE_1001` 命中 100+（已截断），横跨 8 类语义 |
| 限流抛 `CODE_1001` | `GlobalOperationAspect:151` `CODE_1001, "请求过于频繁，请稍后再试"` |
| 验证码两处抛 `CODE_1001` | `AccountController:144`（已过期）、`:147`（不正确）|
| 限流阈值/窗口均 60 | `RATE_LIMIT_PER_MINUTE = 60`、`RATE_LIMIT_WINDOW_SECONDS = 60` |
| 限流端点共 4 个，全为未登录端点 | `login` / `register` / `sendEmailCode` / `resetPassword`（`checkRateLimit = true`）|
| **前端不按 1001 分支** | `Request.js` 响应拦截器只认 `code == 0` / `code == TOKEN_EXPIRED(2001)` / 其他一律 Toast `message` |
| `ErrorCode.PARAM_ERROR: 1001` **定义了从未使用** | `Request.js:21`，全仓无引用 |
| 登录页已有 60s 倒计时与 `clearVerify()` | `Login.vue:205` `codeCountdown`、`:282` `clearVerify()` |

## 2. 架构决策（ADR）

### ADR-001：只拆「客户端需特殊处理 + 监控需单独告警」两类，其余保持 `CODE_1001`

**决策**：新增 `CODE_1004`（请求过于频繁）、`CODE_1005`（验证码错误或过期），仅替换 3 处调用点（限流 1 + 验证码 2）。其余 90+ 处**一律不动**。

**理由**：其余调用点的用户处理方式高度一致（都是「你的输入有问题，去改」），拆开只增加维护面与回归风险，**用户可感收益为零**。而限流与验证码的处理动作与之**本质不同**（前者需等待、后者需重输），故值得独立成码。

**⚠ 代价**：语义仍不完全正交 —— 「参数校验」与「业务规则校验」仍共用 1001。本 Change **接受该代价**，并在 spec 中如实写明边界，不得宣称「错误码已完全语义化」。

### ADR-002：客户端倒计时用**已知固定窗口**，不为传「剩余秒数」扩契约

**决策**：`Request.js` 收到 `CODE_1004` 时，把拒绝对象额外带上 `rateLimitSeconds: 60`（本地常量）。**不**给 `Result` 增加字段。

**理由**：为传一个服务端已知的常量而扩响应结构，是**用契约膨胀换零信息**。窗口是 `RATE_LIMIT_WINDOW_SECONDS`（60），客户端直接用它即可。

**风险与缓解**：若服务端日后改窗口，客户端倒计时会与真实窗口脱节 → **由门禁做静态对账**（T6）：
断言 `Request.js` 的 `RATE_LIMIT_SECONDS` 与 `GlobalOperationAspect.RATE_LIMIT_WINDOW_SECONDS` **相等**。
两者一旦漂移即报红。这比在响应里塞字段更早发现问题。

### ADR-003：验证码失败由客户端**清空并重新获取**，不在服务端改

**决策**：`CODE_1005` 触发 `Login.vue` 的 `clearVerify()` + 重新拉取图形验证码；邮箱验证码**不自动重发**（会再撞限流），仅聚焦输入框并提示。

**理由**：`AccountController` 的 register/login 在 `finally` 里会 `delete` 验证码键 —— 即失败后该验证码**已失效**，用户必须重新获取。客户端主动 `clearVerify()` 可避免用户对着一个已失效的码反复重试。

**为何不自动重发**：`sendEmailCode` 本身**受同一限流约束**（60/分钟）。失败后立刻自动重发 = 立刻再撞限流，只会把一次失败变成连续失败。

### ADR-004：新增门禁 `verify_error_code.mjs`，锁住分段与前后端同步

**决策**：新门禁断言三条 —— ① 后端每个码落在 `ResponseCodeEnum` 自身 javadoc 声明的段内；
② 前端 `ErrorCode` 枚举与后端**双向对账**（前端多出的/后端没有的都要报红）；
③ 本次新增的码在**前端确实被使用**（防止再出现「定义了从未使用」）。

**为何必须新建而非并入 `check-api-contract.mjs`**：那道门禁管的是「路由与调用路径」，错误码分段是另一维度；混入会让失败原因不聚焦（同 `verify_turn_config` 那次因夹具冲突而必须新建的同款理由）。

## 3. 关键实现细节

### 3.1 新码定义（落在通用段 1000-1999，符合 §3.1）

```java
CODE_1004(1004, "请求过于频繁，请稍后再试"),
CODE_1005(1005, "验证码错误或已过期"),
```

### 3.2 前端拒绝对象扩展（**不破坏既有 shape**）

`Request.js` 默认分支改为：
```js
return Promise.reject({ showError, msg, code: responseData.code, ...(extra) })
```
现有调用方只读 `showError` / `msg`，新增字段对它们**无感**。

## 4. 数据影响

**无**。不改表、不改字段、不写迁移。

## 5. 依赖

**不新增任何依赖**（前后端均无）。

## 6. 风险与回退

| 风险 | 缓解 | 回退 |
|---|---|---|
| 老客户端不认新码 | 已实测：落入「其他错误」分支 → 照常 Toast `message`，**行为与现在一致** | — |
| 客户端倒计时与真实窗口脱节 | 门禁静态对账（T6） | 改回 `CODE_1001` |
| 有人按 code 统计的看板失效 | 1004/1005 是**新增**码，旧看板统计 1001 时计数下降 —— 需在 changelog 注明 | 同上 |

**回退总成本**：把 3 处调用点改回 `CODE_1001` + 前端回退分支。**无数据迁移、无接口结构变更。**

## 7. 已知边界（如实登记，不假装已解决）

1. `CODE_1001` 仍承载 8 类语义中的 6 类 —— **本 Change 有意不处理**（ADR-001）。
2. 限流为**固定窗口**计数器（非滑动窗口/令牌桶），突发边界下窗口可能不足 60 秒 ——
   **本 Change 不改限流算法**，仅让客户端知道「要等」。
